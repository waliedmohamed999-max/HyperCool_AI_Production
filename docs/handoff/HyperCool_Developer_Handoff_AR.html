HyperCool — تقرير التسليم الفني الشامل للمبرمج

تاريخ المراجعة: 10 سبتمبر 2026 — إصدار التقرير 1.0

المشروع: HyperCool AI CMO & Sales Operating System. مجلد العمل: E:\xampp\HyperCool_AI_Production. إصدار package.json: 0.5.0.

هذا التقرير يصف الملفات الموجودة وقت المراجعة، ويقارنها بالنطاق المطلوب. لا يفترض أن كل بطاقة في الواجهة تمثل تكاملًا عاملًا. لم تُقرأ مفاتيح .env أو تُنسخ بيانات العملاء أو كلمات المرور إلى التقرير. أسماء المتغيرات أدناه أسماء إعدادات فقط. لا توجد هنا شهادة بإتمام اتصال حي بحسابات المنصات.

الأسماء التجارية وروابط المنصات الواردة في مستند النطاق مرجع متطلبات، وليست نتيجة تحقق خارجي جديد. التقرير ليس سجل commits؛ لا يمكن نسب كل تعديل إلى شخص أو توقيت دون تاريخ مستودع موثق. تقرير الواجهة السابق يوثق مرحلة سابقة؛ أضيفت بعدها وحدات محتوى وذاكرة وتكاملات وفريق أحدث، وتشملها هذه النسخة.

1. الملخص التنفيذي

المنصة حاليًا تطبيق تشغيل محلي ذو واجهة عربية ومصادقة وقاعدة بيانات ومجموعة خدمات أعمال فعلية. تدير المسودات والمراجعة والاعتماد والتقويم وCRM والذاكرة والتقارير، وبها محرك موحد لتشغيل 12 وكيلًا. ليست مجرد صفحات تصميم، وليست بعد منصة تسويق ومبيعات مستقلة مكتملة تعمل على جميع القنوات الخارجية.

يوجد كود اتصال حقيقي بـAnthropic للتوليد والامتثال والمحرك، وكود لاستيراد منتجات سلة. أما إرسال واتساب والبريد والنشر الاجتماعي وتوليد التصميمات ومزامنة الطلبات، فأدواتها الحالية تعيد حالة صريحة بأن التكامل مطلوب. وضع token لهذه الأدوات لا يحولها تلقائيًا إلى موصل عامل؛ يلزم بناء الكود أيضًا.

الجدولة الداخلية موجودة فعلًا وتبدأ مع npm start. تنفيذ الاختبارات الحالية أثبت نجاح 145 اختبارًا. اختبار رحلة الواجهة الأقدم توقف عند selector لزر ذاكرة تغير اسمه؛ لذلك لا يصح وصف اختبارات E2E الحالية بأنها كلها ناجحة اعتمادًا على تقرير سابق من 40 شاشة. فحص تسليم مستقل فتح الأربعين حالة عرض الحالية دون أخطاء JavaScript أو تجاوز أفقي، لكنه رصد ضعف تباين ألوان في كل الحالات؛ هذه ملاحظة قائمة في النسخة المفحوصة.

أهم أولويات المبرمج: تثبيت نسخة مرجعية واختبارات الواجهة، توحيد عقود وصلاحيات الوكلاء، معالجة ثغرات الربط بين الأهلية والتنفيذ، تأمين التشغيل المستضاف، ثم بناء موصل خارجي واحد كامل واختباره قبل توسيع القنوات.

4. المعمارية وكيف يمر الطلب

مسار الاستخدام البشري:

Browser / index.html
  -> public/app.js + وحدات الصفحات
  -> fetch(JSON) + Cookie + X-CSRF-Token
  -> src/server.js: routing/auth/validation
  -> خدمة الأعمال: domain / crm / planning / knowledge / reporting
  -> SQLite + سجل العملية
  -> JSON response
  -> إعادة عرض البيانات والمكونات

مسار الوكيل:

حدث CRM أو تشغيل يدوي أو Scheduler
  -> Frost / EventBus
  -> AgentRuntime
  -> Prompt + JSON Schema + أدوات مسموحة بالمستوى
  -> Anthropic tool-use loop
  -> إعادة فحص صلاحية كل أداة على الخادم
  -> تنفيذ محلي أو INTEGRATION_REQUIRED
  -> تحقق القرار النهائي + حفظ التشغيل والأدوات والتصعيد

createApp({dataDir,env,fetcher}) نقطة الإنشاء المهمة. يسمح بحقن قاعدة مؤقتة ومزود fetch للاختبارات. لا يبدأ المؤقت بمجرد import؛ كتلة تشغيل src/server.js هي التي تستدعي scheduler.start().

التطبيق single-process وsingle-workspace. لا يوجد tenantId أو عزل مؤسسات أو اشتراكات وفوترة SaaS. المظهر شبيه بمنصات SaaS، لكن المعمارية التشغيلية ليست منصة متعددة المستأجرين.

7. الحسابات والصلاحيات والأمان الموجود

ثلاثة أدوار فقط: owner وoperator وreviewer. أول استخدام ينشئ المالك دون كلمة مرور افتراضية. كلمة المرور 12–256 حرفًا، والاسم 100 حرف، وusername من 3–40 حرفًا إنجليزيًا/رقمًا/علامات مسموحة، ثم يُحفظ lowercase.

كلمات المرور salted scrypt. الجلسة عشوائية ويخزن hash الرمز في القاعدة، مدتها ثماني ساعات. Cookie اسمها hc_session مع HttpOnly وSameSite=Strict؛ لا Secure في إعداد localhost HTTP الحالي. المحاولات محدودة بعشر محاولات لكل IP ضمن 15 دقيقة، محفوظة في الذاكرة وتُصفّر بإعادة التشغيل. لا MFA ولا SSO ولا استعادة ذاتية بالبريد.

كل API محمي بعد setup/login/auth يتطلب جلسة، والكتابات تتطلب X-CSRF-Token. توجد قيود Host على localhost/127.0.0.1، والتحقق من Origin وsec-fetch-site، وحد جسم JSON 64KB، وnosniff، وCSP للملفات الثابتة.

إدارة الفريق الأحدث تشمل إنشاء عضو، تغيير دوره، إيقافه، إعادة تفعيله، حذفه، إعادة تعيين كلمة مروره بواسطة المالك، وإلغاء جلساته. توجد حماية من ترك النظام بلا مالك نشط. لا دعوات بريدية فعلية، ولا كلمات مرور مؤقتة بفرض تغيير عند أول دخول. وجود جلسة غير منتهية لا يثبت أن المستخدم متصل أو ينظر إلى الشاشة الآن.

المراجعة والاعتماد يمكن أن يجريهما نفس المالك؛ فصل الشخصين لم يُفرض في الكود.

إنشاء المحتوى يقبل Instagram وFacebook وX وLinkedIn. العنوان حتى 200 حرف، النص العربي والإنجليزي حتى 10,000 لكل منهما. رابط المنتج يجب أن يكون HTTPS وعلى hyper-cool.com دون بيانات دخول في الرابط. الأصل البصري رابط HTTPS، وليس رفع ملف إلى التطبيق.

المراجع يسجل evidence ويؤكد facts/claims/link؛ وإذا وُجد أصل بصري يؤكد asset. الاسم والهوية الحقيقيان يؤخذان من الجلسة على الخادم. المراجعة تخزن SHA-256 لمحتوى يشمل العنوان والنصين والرابط والأصل والمنصة والتاريخ. الاعتماد يعيد فحص البصمة ويخزنها، فلا يُعاد استخدام اعتماد نص قد تغير.

التوليد من واجهة الكتابة يتطلب منتجًا مستوردًا معروضًا للبيع وبياناته أحدث من 24 ساعة، ونبرة علامة معتمدة، ومواصفة معتمدة مرتبطة بالمنتج. يمنع السياق التصريح بالأسعار والتوفر والادعاءات الطبية في هذا المسار. يدعم brief إضافيًا للحملة والجمهور والنوع واللغة والنبرة وCTA ومرحلة funnel وكلمات SEO والعرض والطول والمرجع، مع حدود طول.

requestKey والبصمة وصاحب الطلب تمنع تكرار نفس العملية أو استخدام المفتاح لطلب مختلف. التوليد المباشر يسمح بطلب نشط واحد في العملية. الطلبات RUNNING عند إعادة التشغيل تُوسم INTERRUPTED بدل إعادة دفع استدعاء مدفوع تلقائيًا. يعاد فحص السياق بعد رجوع النموذج قبل إنشاء المسودة.

الفحص الآلي للامتثال مسار مستقل مقيد بـDRAFT وبصمة وطلب وهوية. يعرض تصنيفًا ومشكلات وتصحيحات/أدلة مطلوبة. هو مساعد للمراجع وليس آلة لإثبات حقيقة الادعاء أو بديلًا عن اعتماد الإنسان.

9. التقويم والجدولة وn8n

إنشاء التقويم يبني 30 يومًا بقواعد ثابتة: Instagram/X/Facebook يوميًا، وLinkedIn الأحد والثلاثاء والخميس. لا يولد ذلك 30 منشورًا ولا تصميمًا تلقائيًا، بل خانات وأفكار/محاور. قيد date/platform يمنع التكرار عند تداخل التقويمات.

الجدولة تتطلب اعتمادًا ومراجعة موثقين وبصمة مطابقة، موعدًا مستقبليًا بمنطقة زمنية، وتوافق تاريخ الرياض مع تاريخ المحتوى. LinkedIn يتطلب النص الإنجليزي واليوم المسموح؛ Instagram يتطلب أصلًا بصريًا. لا توجد خانة ثانية لنفس المنصة واليوم في هذا النموذج.

الحالات: SCHEDULED ثم READY_FOR_CONNECTOR أو BLOCKED، مع CANCELLED عند الإلغاء. لحظة الاستحقاق يعاد فحص الاعتماد. READY_FOR_CONNECTOR لا يعني نُشر ولا أُرسل. يوجد idempotencyKey، لكنه ليس بمفرده ضمان إرسال خارجي مرة واحدة؛ ذلك يتطلب تنفيذ connector وتسوية مع مزوده.

الحزمة اليومية لقطة واحدة لكل يوم، تحتوي قرارات ومحتوى الغد والفجوات والجدولة الموقوفة. لا ترسل تلقائيًا إلى البريد أو واتساب. التقرير الأسبوعي لقطة واحدة لكل أسبوع.

المجدول الداخلي يفحص كل 300,000ms افتراضيًا. ينشئ الحزمة أثناء الساعة 08 بتوقيت الرياض، ويحاول حفظ التقرير يوم الأحد، ويفحص فجوات المتابعة كل tick. يبدأ بعد أول interval، وليس cron عند الثانية 00 بالضبط. run-now يستدعي tick نفسه؛ خارج الساعة 08 لا يفرض إنشاء الحزمة اليومية.

ملف n8n يملك مسارين: حزمة 08:00 وتجهيز المواعيد كل خمس دقائق، بمفتاح X-HyperCool-Token. يحتاج n8n قادرًا على الوصول إلى loopback الصحيح. 127.0.0.1 داخل Docker أو n8n Cloud ليس حاسوب التطبيق. لا يوجد إثبات تفعيل workflow في n8n ضمن هذه المراجعة.

تنبيه للمبرمج: المجدول الداخلي الحالي لا يستدعي prepareDue للنشر؛ توجد العملية يدويًا أو عبر n8n. كذلك pause gate يغطي scheduler/event routing، ولا يتحقق منه مسار n8n automation؛ حدّد هل المطلوب أن يشمل الإيقاف كل مصادر الأتمتة.

لا نشر يومي حقيقي للقنوات الأربع. لا inbound webhook موحد لمحادثات المنصات. لا إرسال أو متابعة خارجية فعلية. لا عروض سعر رسمية أو PDF مستقل أو تحويل دفع/طلب متجر. لا بحث سوق/عملاء آلي موثق متصل بالويب. لا Canva asset فعلي أو مكتبة رفع ملفات/تحقق أبعاد وصيغ. لا GA4/UTM/attribution أو مزامنة نتائج اجتماعية. لا loop تعلم يقيس نتيجة منشور حقيقي ثم يغير استراتيجية مستقبلية تلقائيًا بضوابط.

لا multi-tenancy أو billing أو تطبيق هاتف مستقل أو إدارة مهام مسندة للأفراد أو دعوات فريق بالبريد أو OAuth token rotation أو SSO/MFA. لا CI/CD أو Docker deployment أو OpenAPI أو مراقبة تشغيل مركزية ثبت وجودها في قائمة الملفات المفحوصة. هذه ليست كلها ضرورية للنسخة المحلية، لكنها لا يجوز الادعاء بوجودها.

21. خطة استكمال عملية للمبرمج

الحزمة الأولى: تثبيت النسخة وإزالة الالتباس

احفظ نسخة مصدر موثقة مع lockfile وبصمات ودون أسرار، وحدّث اختبارات UI والوثائق ومصفوفة الصلاحيات. افحص المسارات التي يقرأها reviewer، وإغلاق التصعيد، ومعنى L0، وربط أهلية الترقية. معيار القبول: unit/API/E2E ناجحة للثلاثة أدوار، وعدم الاعتماد على إخفاء زر للحماية.

الحزمة الثانية: تقوية Runtime والجدولة

وحّد إعداد AI وعقود الأدوات، وأزل تضارب prompt، وأضف قفل tick وbackoff وحدود تكاليف وتعافي التشغيلات. ضع outbox أو queue مناسبة للحجم. معيار القبول: اختبارات انقطاع وإعادة تشغيل وتكرار و429 وtimeout دون كتابة مضاعفة أو إرسال غير معتمد.

الحزمة الثالثة: اتصال إنتاجي واحد كامل

اختر مع مالك المشروع أولوية واضحة: قناة WhatsApp/البريد للمبيعات أو منصة نشر للمحتوى. نفّذ الحساب والتفويض والموصل وwebhook إن لزم وتخزين external IDs وإعادة المحاولة والموافقة. معيار القبول: حدث حقيقي واحد كامل موثق ثم تجارب failure، دون تعميم نجاح خدمة على الخدمات الأخرى.

الحزمة الرابعة: المحتوى والتصميم والنشر

اربط الأصل البصري والنسخ والامتثال والجدولة بموصل النشر، وأضف فحص متطلبات media لكل منصة وحالة منشور ورابطه. معيار القبول: نشر محتوى معتمد فقط، وإلغاء اعتماد نسخة معدلة، وتتبع فشل/نجاح فعلي بدل READY_FOR_CONNECTOR.

الحزمة الخامسة: المبيعات والطلبات والقياس

استقبال رسائل حقيقية، ردود ضمن سياسة الحساب، متابعة بموافقة القناة، quotes وorders، ثم attribution وKPIs. معيار القبول: سيناريو عميل كامل من رسالة إلى قرار/إغلاق، مع opt-out ومنع التكرار وتدخل بشري.

الحزمة السادسة: الإطلاق والمراقبة

تهيئة الاستضافة/HTTPS والجلسات وbackup/restore والمراقبة والسجلات والمناوبات. نفّذ تجربة فعلية بأهداف النطاق الأصلية ثم قيّم الاستقلالية تدريجيًا. لا يُحدد زمن/سعر كل حزمة دون اختيار القناة وحساباتها وحجم البيانات ومستوى الضمان المطلوب.

22. البيانات والقرارات المطلوبة من صاحب المشروع

حسابات المنصات الرسمية وصاحب صلاحية التفويض، وتحديد Instagram الأساسي وFacebook، وبيانات Anthropic وسلة عبر قناة أسرار آمنة. مصادر المنتجات والأسعار والادعاءات والسياسات والضمان والشحن والخصومات المعتمدة. حدود الصفقات والتصعيد وساعات العمل ومسؤول المراجعة. تحديد ما إذا كان فصل المراجع عن المعتمد إلزاميًا، وما إذا كان L0 يسمح بتعديلات CRM محلية. اختيار قناة الإطلاق الأولى وسياسة نشر المحتوى واستضافة النظام ومدة الاحتفاظ بالبيانات.

23. قائمة استلام المبرمج

1. افتح package.json وREADME وهذا التقرير، ثم راجع server.js قبل البدء في تعديل UI.

2. ثبت Node وnpm ci وشغّل 145 اختبارًا؛ وثق أي فرق في العدد أو النتائج.

3. افحص artifacts/handoff/evidence.json وبصمات الملفات لمطابقة لقطة التقرير.

5. اقرأ domain/planning لمعنى البصمة والاعتماد قبل تعديل محتوى معتمد.

8. حدث اختبارات UI بعد تغييرات النصوص والـIDs ولا تترك نجاح unit tests يغطي تعطل الرحلة.

9. لا تعتبر token موجودًا أو badge CONNECTED دليل اتصال؛ اطلب تنفيذًا حيًا موثقًا آمنًا.

10. سلّم changelog واختبارات وbackup/restore وخطة رجوع مع كل إصدار قابل للتشغيل.
