# دليل ربط وكلاء HyperCool وتجهيز الموقع للنشر

دليل تنفيذ عربي • تاريخ المراجعة: 20 سبتمبر 2026 • النسخة: 1.0

## 1. ما الذي تمت مراجعته؟

هذا الدليل مبني على الكود الحالي داخل `_public-site-worktree`، وهي النسخة التي تحتوي على صفحة واتساب التي تم تعديلها، وعلى مراجعة وثائق الخدمات الرسمية. ليس شهادة بأن حساباتك الخارجية متصلة أو أن الموقع المنشور اجتاز الاختبار.

تم حصر **13 وكيلًا** من `src/domain.js`، ومراجعة أدواتهم وتدفقات الربط وواجهات الإعداد. تم تشغيل `npm run production:check` محليًا في هذه النسخة. لم يتم إدخال مفاتيح، أو ربط حسابات، أو إرسال رسائل، أو نشر محتوى أثناء إعداد هذا الملف.

**نتيجة الفحص المحلي: غير جاهز للنشر بإعداداته الحالية.** ثلاثة موانع صريحة: `NODE_ENV` غير مضبوط على `production`، و`INTEGRATION_ENCRYPTION_KEY` غير موجود، و`PUBLIC_ORIGIN` غير موجود. ظهر أيضًا عدم إعداد بريد المنصة ومزود AI على مستوى الخادم ومجلد البيانات ومدير المنصة في سياق هذا الفحص.

ملف `.env` غير موجود داخل النسخة المراجعة. ملف `.env` في جذر المشروع الآخر يحتوي على متغير واحد غير فارغ خاص بمدير المنصة؛ لم تُنسخ قيمته إلى التقرير. إعدادات خادم الإنتاج وخزنة اتصالات قاعدة البيانات لم تُراجع، ولذلك لا نستنتج عدم وجود اتصالات محفوظة من غياب ملفات البيئة المحلية.

يوجد اختلاف بين بعض الوثائق القديمة والكود: استقبال رسائل وتعليقات Meta، ومزامنة تحليلات التسويق، وحوكمة الموصلات المخصصة، وإعادة محاولة بعض أحداث Webhook موجودة في النسخة الحالية؛ لا تُعاملها كميزات مفقودة اعتمادًا على الوثائق القديمة.

## 2. ابدأ بهذا الترتيب

| الترتيب | المطلوب منك | معيار إتمام الخطوة |
|---|---|---|
| 1 | تحديد نسخة المشروع التي ستُنشر، والدومين، وخادم Node.js دائم التشغيل | فتح `/app` على HTTPS من الدومين المقصود |
| 2 | إعداد وضع الإنتاج ومفتاح التشفير ومسار بيانات دائم | زوال موانع `production:check` |
| 3 | إعداد حساب المالك ومدير المنصة وبريد Resend | وصول دعوة واستعادة كلمة مرور حقيقيتين |
| 4 | ربط OpenAI أو Anthropic؛ مزود واحد كافٍ للبداية | نجاح اختبار الاتصال ثم تشغيل وكيل فعلي |
| 5 | تعبئة ذاكرة العلامة والمنتجات وبيانات العملاء التجريبية | إجابات مستندة إلى بيانات معتمدة |
| 6 | ربط سلة ومزامنة المنتجات إن كان متجرك يستخدمها | تطابق منتج وسعر ومخزون مع المتجر ووقت المزامنة |
| 7 | ربط واتساب واختبار Webhook والقوالب | ظهور رسالة واردة وحالة تسليم لرسالة اختبار مصرح بها |
| 8 | ربط Microsoft 365 والقنوات الاجتماعية المطلوبة | نجاح اختبار كل وظيفة، وليس علامة «متصل» فقط |
| 9 | تعيين الاتصالات لكل وكيل وأداة ومعالجة النواقص في القسم 10 | عدم وجود عائق في الأدوات التي ستستخدمها |
| 10 | إطلاق تجريبي محدود ثم فتح الميزات تدريجيًا | نسخة احتياطية قابلة للاستعادة وسجل تشغيل مستقر |

لا تحتاج حسابًا أو مفتاح AI منفصلًا لكل وكيل. يمكن للـ13 وكيلًا مشاركة اتصال ذكاء اصطناعي واحد، مع إمكانية تخصيص اتصال أو نموذج مختلف لوكيل معين. مفتاح AI لا يربط واتساب أو سلة تلقائيًا.

## 4. طريقة الربط المشتركة لكل وكيل

1. سجل الدخول بمالك مساحة العمل الصحيحة.
2. افتح مركز الربط والتحكم. أضف اتصال OpenAI أو Anthropic باسم واضح، ثم أدخل المفتاح في حقل السر المخصص واختبره. يلزم إعداد مفتاح تشفير الخادم قبل حفظ الأسرار في الخزنة.
3. اجعل اتصال AI مناسبًا كافتراضي للمساحة أو اختره صراحة في إعداد كل وكيل. ترتيب الاختيار في التشغيل: اتصال الوكيل، ثم افتراضي المساحة، ثم إعداد البيئة القديم.
4. افتح فريق الوكلاء، ثم إعداد الوكيل. فعّله، وحدد اتصال AI واسم نموذج متاح في حسابك. لا تفترض أن كل نموذج يدعم نفس المعاملات.
5. من أدوات الوكيل اختر الاتصال الذي يخص نفس مساحة العمل ويمنح القدرة المطلوبة. عند تعدد المتاجر أو الحسابات، عيّن الحساب صراحة ولا تعتمد على الاختيار التلقائي.
6. ابدأ بمستوى `L0` للمهام الداخلية، ثم `L1` للمهام التي تحتاجه تحت الإشراف. أدوات النشر الاجتماعي تتطلب `L2` للوكيل `publishing`، ولن تعمل بينما سقف النظام `PRODUCTION_SAFE` يقيّد التنفيذ إلى `L1`.
7. راجع «جاهزية الوكيل» وخريطة الوكيل ← الأداة ← الاتصال، ثم نفّذ الاختبار المذكور لكل وكيل أدناه.
8. احتفظ بسجل الاختبار: الوكيل، اتصال الخدمة، النموذج، وقت التنفيذ، النتيجة، والخطأ إن وجد؛ دون تسجيل المفاتيح أو رموز الدخول.

حالة `READY` لا تثبت اكتمال عمل القنوات الخارجية؛ سياسة الجاهزية تعتبر كثيرًا من أدواتها اختيارية. كما أن `L0` يسمح ببعض عمليات الكتابة الداخلية، مثل إنشاء مسودة أو سجل عميل، ولا يعني قراءة فقط.

### معاني حالات الربط

| الحالة | معناها والإجراء |
|---|---|
| `WAITING_LLM` | مزود AI أو نموذجه غير جاهز؛ افحص المفتاح والنموذج والرصيد |
| `CONNECTION_REQUIRED` | الأداة تحتاج اتصالًا؛ أنشئه ثم عيّنه |
| `CONNECTION_SELECTION_REQUIRED` | توجد اتصالات متعددة دون اختيار واضح |
| `CONNECTION_UNHEALTHY` | الاتصال لا يعمل؛ اختبره وافحص رمز الخطأ |
| `CONNECTION_CAPABILITY_MISSING` | الصلاحيات لا تغطي المهمة؛ امنح الصلاحية ثم أعد التفويض |
| `REAUTH_REQUIRED` / `TOKEN_EXPIRED` | أعد تسجيل الدخول للخدمة وجدد الاتصال |
| `NOT_IMPLEMENTED` | نقص برمجي؛ إضافة مفتاح لا تكفي |
| `NOT_AVAILABLE` / `PARTIAL` | بيانات أو مقاييس غير متاحة؛ لا تُفسرها على أنها صفر |

## 5. جميع الوكلاء: الربط والاختبار والنواقص

### 01 — Frost لإدارة المنظومة — `frost`

**الدور:** ترتيب الأولويات وتنسيق سير العمل. **الربط:** مزود AI، البيانات الداخلية، وMicrosoft 365 فقط إذا أردت قراءة المواعيد أو إنشاء اجتماع. أدوات التقويم المعنية: `get_calendar_availability` و`create_calendar_event`.

**ما تجهزه:** أهداف النشاط، سياسات التصعيد، مهام ومحتوى وعملاء داخل النظام. **اختبار القبول:** اطلب أولويات اليوم من السجلات الموجودة، وتأكد أن كل مهمة تشير إلى بيانات حقيقية. **النقص المحتمل:** لا ينتج تقييمًا مفيدًا من مساحة فارغة، ولا يصبح جميع الوكلاء جاهزين لمجرد نجاح تشغيل Frost.

### 02 — استراتيجية المحتوى — `strategy`

**الربط:** AI وأداة `search_brand_memory`؛ ويمكن استخدام `get_competitor_data` لمعلومات المنافسين المسجلة. لا يحتاج اشتراك سوشيال مستقل لإنشاء خطة.

**ما تجهزه:** الجمهور والأهداف والقنوات والمواسم والميزانية التحريرية وحقائق المنتجات. **اختبار القبول:** خطة أسبوع مرتبطة بهدف مبيعات، بلا ادعاءات غير مسجلة. **النقص:** أبحاث المنافسين لا تُجلب من الإنترنت تلقائيًا؛ تعتمد على ذاكرة العلامة المعتمدة.

### 03 — كتابة المحتوى — `copy`

**الربط:** AI و`search_brand_memory`، مع `create_content` عندما تحتاج حفظ مسودات داخل النظام. **ما تجهزه:** نبرة العلامة، أمثلة معتمدة، المنتج، الرابط، السعر ومصدره، اللغة والمنصة.

**اختبار القبول:** إنتاج مسودتين بالعربية والإنجليزية وحفظ المحتوى كمسودة خاضعة للمراجعة. **النقص:** روابط المنتجات في `src/domain.js` مقيدة حاليًا بـ`hyper-cool.com`؛ قبل استخدام المنصة لعلامات أو متاجر أخرى يجب تحويل هذا القيد إلى إعداد لكل مساحة عمل.

### 04 — التصميم — `creative`

**الربط المتاح:** AI و`search_brand_memory` لإعداد تصور بصري ووصف التصميم وسيناريو الفيديو. **الربط غير المنفذ:** `canva_generateAsset` معلّمة `isAvailable:false`.

**ما تجهزه:** الشعار، الألوان، المقاسات، صور المنتجات وحقوق استخدامها. **اختبار القبول الحالي:** وصف تصميم واضح يمكن للمصمم تنفيذه. **النقص:** لا تتوقع صورة أو فيديو مولدًا فعليًا؛ `CANVA_API_KEY` وحده لا يشغّل التوليد. مؤقتًا جهّز الأصل يدويًا واربطه برابط HTTPS يمكن للمنصة الناشرة الوصول إليه. وجود Canva كأداة في بيئة المساعد لا يثبّت تكاملًا في موقعك.

### 05 — مراجعة الامتثال — `compliance`

**الربط:** AI و`search_brand_memory`، مع بيانات المنتج الموثقة عند التحقق من سعر أو مواصفة. **ما تجهزه:** سياسة الأسعار والخصومات والضمان والمواصفات والادعاءات المسموح بها والممنوعة.

**اختبار القبول:** قدّم مسودة تتضمن سعرًا أو ادعاءً غير موثق؛ يجب طلب بيانات أو إيقافها للمراجعة. **النقص:** النموذج لا يعوض عن سياسة غير مكتوبة، والموافقة على المحتوى لا تمنح وحدها صلاحية النشر.

### 06 — النشر والجدولة — `publishing`

**الربط:** AI ثم القنوات المطلوبة: `meta_publish` لفيسبوك/إنستغرام، `x_publish` لـX، و`linkedin_publish` لصفحة LinkedIn. لا يلزم ربط جميع القنوات إذا لن تستخدمها.

**ما تجهزه:** حسابات الأعمال وصلاحيات النشر ومحتوى `APPROVED` وأصل بصري لإنستغرام. **اختبار القبول:** نشر عنصر اختبار معتمد والحصول على معرف منشور حقيقي وعدم تكراره عند إعادة المحاولة. **موانع قبل التفعيل:** نقص صلاحية فيسبوك، وخطأ scope في X، والتحقق من صلاحيات LinkedIn وإصدارات API؛ راجع القسم 10. التنفيذ يتطلب `L2` ورفع سقف النظام المناسب وتفعيل مفاتيح النشر بعد قبول اختبارات المرحلة التجريبية؛ لا تتجاوز قواعد الترقية المطبقة.

### 07 — العملاء المحتملون — `leads`

**الربط:** AI و`create_lead` و`search_crm`. سلة اختيارية لـ`get_current_price` و`get_stock`. مصادر العملاء الفعلية تكون CRM أو القنوات الواردة أو بيانات تضيفها.

**ما تجهزه:** اسم العميل والشركة ووسيلة الاتصال ومصدر الفرصة وتاريخه والاهتمام والموافقة على التواصل. **اختبار القبول:** إضافة فرصة بمصدر واضح ثم العثور عليها داخل CRM. **النقص:** لا يوجد ضمن هذه الأدوات محرك بحث ويب أو قاعدة عملاء تجارية مدمجة؛ لا تعتبر الوكيل أداة استخراج عملاء من الإنترنت تلقائيًا.

### 08 — المحادثات والمبيعات — `sales`

**الربط الأساسي:** AI و`get_lead` و`create_lead` و`update_lead` و`search_crm`. **الربط الخارجي حسب القناة:** سلة للمنتجات والأسعار والمخزون، واتساب للإرسال، Meta للردود الخاصة، Microsoft للبريد والمواعيد.

**أدوات مهمة:** `get_product`، `get_current_price`، `get_stock`، `whatsapp_send`، `whatsapp_campaign_send`، `meta_message_send`، `microsoft_sendEmail`، `create_calendar_event`، `get_calendar_availability`.

**اختبار القبول:** سؤال وارد من عميل تجريبي عن منتج معروف، إجابة مبنية على آخر مزامنة، تسجيل المحادثة والتأهيل، ثم موافقة بشرية عند الحاجة. **النواقص:** السعر والمخزون في الأدوات لقطة من آخر مزامنة وليسا استعلامًا لحظيًا دائمًا؛ تأكد من حداثتهما قبل العرض. تحليل ملفات وصوت العملاء الواردة غير منفذ لمجرد تسجيل بيانات الوسائط. لا تعتبر الرد الصادر مؤكدًا دون معرف إرسال وحالة مناسبة.

### 09 — المتابعة — `followup`

**الربط:** AI و`get_recent_replies` و`create_followup`؛ واتساب أو Microsoft 365 للتواصل الفعلي. يمكن استخدام أدوات التقويم عند تخصيصها بالمستوى المناسب.

**ما تجهزه:** تسلسل متابعة، مواعيد، موافقة العميل، سقف عدد الرسائل، وشروط الإيقاف والتصعيد. **اختبار القبول:** إعداد متابعة تجريبية ثم إدخال رد أو طلب إلغاء اشتراك؛ يجب ألا يستمر الإرسال على نحو يخالف الحالة. **النقص:** إنشاء خطة متابعة أو تشغيل الفحص لا يثبت إرسال رسائل؛ افحص سجل القناة. الحملات الجماعية في واتساب محدودة حاليًا بـ50 مستلمًا في الطلب الواحد.

### 10 — رصد السوق — `intelligence`

**الربط:** AI و`get_competitor_data`. **ما تجهزه:** معلومات المنافسين كمداخل معتمدة من نوع `competitor_insight` مع الرابط والتاريخ.

**اختبار القبول:** تقرير يلخص البيانات المسجلة ويبيّن نقصها أو قدمها. **النقص المؤكد:** الأداة تقرأ الذاكرة المحلية؛ ليست تصفحًا مباشرًا أو رصدًا آليًا للمنافسين. إن أردت رصدًا مستمرًا يلزم مصدر بيانات/موصل إضافي ومسار مراجعة للمعلومات الواردة.

### 11 — قياس الأداء — `performance`

**الربط:** AI و`get_metrics` للتقرير التشغيلي الداخلي. لتحليل السوشيال اربط القنوات ثم شغّل مزامنة التحليلات من صفحة التسويق؛ يوجد مسار فعلي `POST /api/marketing/analytics/sync` ومسار تحليل يستخدم الأدلة المجمعة.

**اختبار القبول:** قارن نتائج المحتوى المنشور بأرقام حسابك عند المصدر، وتحقق أن المقياس غير المتاح يظهر كنقص بيانات. **النواقص:** لا تساوي الأداة الداخلية تلقائيًا كل تحليلات المنصات. الكود الحالي يضع قيمة `saved` في حقل `shares` عند قراءة إنستغرام؛ يجب تصحيح هذا الربط قبل الاعتماد التجاري على تقارير المشاركات. افحص أيضًا صلاحيات Insights وتوافق المقاييس مع إصدار Graph API ونوع المنشور.

### 12 — ذاكرة العلامة — `memory`

**الربط:** AI و`search_brand_memory` و`propose_memory_update`، دون خدمة خارجية لازمة. **ما تجهزه:** الحقائق والسياسات والأسلوب والمصادر ومالك اعتماد المعلومة.

**اختبار القبول:** اقتراح معلومة جديدة؛ تبقى بحاجة لاعتماد بشري قبل اعتبارها حقيقة مرجعية. **النقص:** جودة بقية الوكلاء تعتمد على هذه البيانات؛ أكملها قبل تشغيل مهام مبيعات أو امتثال حقيقية.

### 13 — مساعد غرفة القيادة — `frost_commander`

**الربط:** AI وقراءة الحالة الداخلية، وخريطة اتصالات الوكلاء ومسارات العمل. يدعم طلبات تشغيل محدودة بموافقة، ومعاينة/تنفيذ حملة واتساب عبر `whatsapp_campaign_send` عند جاهزية القناة والسياسات.

**أدوات نموذجية:** `get_company_health`، `get_integrations_health`، `get_agent_tool_status`، `search_context`، `delegate_to_agent`، `create_workflow_draft`، `list_workflows`، `explain_workflow_failure`.

**اختبار القبول:** اسأله «ما الاتصالات الناقصة وما سبب تعطل الوكلاء؟» وقارن النتيجة بخريطة الربط. جرّب إنشاء مسودة سير عمل وتحقق أنها لا تتفعل بلا المراجعة المطلوبة. **القيد:** التفويض المباشر في `delegate_to_agent` محصور حاليًا في `performance` و`intelligence` و`leads` و`strategy`؛ ليس تفويضًا حرًا لكل الـ13 وكيلًا. الوكلاء الفرعيون يحتاجون إعداد AI والبيانات والأدوات الخاصة بهم أيضًا.

## 6. إعداد الخدمات خطوة بخطوة

### 6.1 مزود الذكاء الاصطناعي

لـOpenAI أنشئ مفتاح API في المشروع المقصود واحفظه على الخادم أو في خزنة اتصال الموقع، ثم حدّد اسم نموذج متاح لحسابك. توصي [وثائق OpenAI الرسمية](https://developers.openai.com/api/docs/quickstart) بإنشاء المفتاح واستخدامه من البيئة الآمنة للتطبيق.

```dotenv
AI_PROVIDER=openai
OPENAI_API_KEY=REPLACE_WITH_SECRET
OPENAI_DEFAULT_MODEL=REPLACE_WITH_AVAILABLE_COMPATIBLE_MODEL
```

أو استخدم Anthropic وفق [توثيق Claude API](https://platform.claude.com/docs/en/api/overview):

```dotenv
AI_PROVIDER=anthropic
ANTHROPIC_API_KEY=REPLACE_WITH_SECRET
ANTHROPIC_MODEL=REPLACE_WITH_AVAILABLE_COMPATIBLE_MODEL
```

اختر إحدى الطريقتين كبداية. إعداد المفتاح من مركز الربط يتيح الفصل بين مساحات العمل، بينما متغيرات الخادم تمثل افتراضيًا احتياطيًا قد تشترك فيه مساحات غير مخصصة.

**تنبيه مثبت من مسار التشغيل:** سجل الوكلاء يبدأ بقيمة مزود `anthropic`، ومسار التشغيل القديم يمرر هذه القيمة صراحة عندما لا يوجد اتصال AI معين. لذلك لا تعتمد على `AI_PROVIDER=openai` وحده لتغيير الوكلاء الموجودين. اختر اتصال OpenAI صراحة للوكيل/المساحة، أو حدّث مزود الوكيل من إعداد النموذج القديم عبر `POST /api/agents/{agentId}/model-config` ثم اختبر المزود المسجل في التنفيذ. هذا اختلاف مهم عن التبسيط الموجود في وثيقة AI القديمة.

**اختباران مطلوبان:** اختبار الاتصال يتحقق من إمكانية الوصول/المصادقة، ثم «اختبار الوكيل» يتحقق من استجابة النموذج والأدوات والخرج المنظم. كود OpenAI الحالي يستخدم `/v1/chat/completions` ويرسل `max_tokens` وقد يرسل `temperature`؛ يجب اختيار نموذج يقبل هذا العقد أو تعديل الموصل. لا تضع اسم «أحدث نموذج» دون تجربة فعلية. لا توجد هنا قائمة أسعار حالية مضمونة، وتقدير التكلفة يحتاج تعبئة أسعار المشروع؛ راقب الفاتورة من لوحة المزود.

### 6.2 سلة

1. افتح بوابة الشركاء وأنشئ تطبيقًا أو اختر التطبيق الحالي، واربطه بالمتجر المقصود.
2. جهّز `SALLA_CLIENT_ID` و`SALLA_CLIENT_SECRET`، وحدد `SALLA_REDIRECT_URI` مطابقًا لمسار الربط المختار في القسم 7.
3. ابدأ بصلاحية قراءة المنتجات؛ الكود يطلب أيضًا `offline_access` و`orders.read` و`customers.read`. طابق القيم المتاحة في لوحة تطبيقك؛ وجود scope لا يعني أن تنفيذ كل عملية موجود في موقعك.
4. من الموقع اضغط ربط سلة ووافق على المتجر، ثم نفّذ مزامنة المنتجات.
5. اختبر منتجًا معروفًا وسعره ومخزونه وطابع المزامنة الزمني.
6. أضف Webhook إلى `/api/webhooks/salla`، واضبط `SALLA_WEBHOOK_SECRET`. إن استخدمت التوقيع فاضبط `SALLA_WEBHOOK_STRATEGY=signature` واسم الترويسة وفق الإعداد الفعلي؛ اختبر حدثًا حقيقيًا وعدم تكراره.

**حدود التنفيذ:** `salla_syncOrders` أصبحت مُنفَّذة — تقرأ أحداث الطلبات (إنشاء/تحديث/اكتمال) التي دفعها المتجر فعليًا عبر Webhook `/api/webhooks/salla`، وليست استدعاء REST حي لنقطة نهاية طلبات سلة (لا يوجد نداء مُتحقق منه لها في هذا الكود)؛ لذلك لا تُرجع شيئًا قبل وصول أول حدث Webhook حقيقي، ولا تكتب الطلبات إلى CRM بعد. مزامنة الكتالوج لا تعني مزامنة الطلبات والسلات المتروكة. المسار القديم ومسار المتاجر المتعددة مختلفان؛ لا تخلط عنوان العودة الخاص بأحدهما مع بدء الآخر.

**نقص عند تعدد المتاجر:** تدفق OAuth لسلة لا يجلب هوية التاجر تلقائيًا. محلل Webhook يستطيع ملء الهوية من أول حدث فقط إذا وجد اتصال سلة واحدًا غير محدد الهوية على مستوى النظام كله. عند وجود أكثر من مرشح سيبقى الحدث غير محلول؛ استكمل جلب وربط Merchant ID الموثوق قبل إطلاق عدة متاجر/مساحات، واختبر التوجيه فعليًا.

**نشر تطبيق في متجر تطبيقات سلة:** مختلف عن نشر موقعك. راجع نمط OAuth ومتطلبات قبول تطبيق الشركاء قبل عرضه لتجار آخرين؛ الربط المحلي الحالي لا يثبت قبول تطبيق عام. مرجع الإعداد: [تفويض سلة](https://docs.salla.dev/421118m0).

### 6.3 Meta: فيسبوك وإنستغرام وواتساب

1. افتح تطبيقات Meta، وأنشئ/اختر تطبيق أعمال يناسب المنتجات المستخدمة. جهّز الصفحة وحساب Instagram المهني وأصول WhatsApp Business وصلاحيات إدارة هذه الأصول.
2. اضبط `META_APP_ID` و`META_APP_SECRET` و`META_REDIRECT_URI` ومفتاح التشفير. سجّل عنوان العودة نفسه في لوحة Meta.
3. اطلب الصلاحيات اللازمة فعلًا. يطلب الكود: `business_management`، `pages_show_list`، `pages_read_engagement`، `pages_manage_metadata`، `pages_messaging`، `instagram_basic`، `instagram_manage_messages`، `instagram_content_publish`، `whatsapp_business_management`، `whatsapp_business_messaging`.
4. **قبل نشر فيسبوك:** استكمل طلب `pages_manage_posts` وتصحيح فحص القدرة؛ هذه الصلاحية غير موجودة ضمن قائمة الطلب الحالية. لا يكفي أن تكون الصفحة متصلة.
5. ابدأ ربط Meta من داخل الموقع، وتأكد من الصفحة والرقم اللذين اختارهما. الكود ينتقي أول صفحة وأول أصول مكتشفة؛ لا توجد واجهة اختيار كاملة لكل الأصول.
6. اضبط `META_VERIFY_TOKEN` بقيمة عشوائية تخصك. التوقيع يستخدم `META_WEBHOOK_SECRET` أو يرجع إلى `META_APP_SECRET`؛ يجب أن يطابق مفتاح توقيع تطبيق Meta الفعلي، وليس Verify Token.
7. اربط مسار واتساب ومسار الرسائل الاجتماعية في القسم 7 بالاشتراكات الخاصة بكل منتج. اختبر وصول رسالة وإسنادها لمساحة العمل الصحيحة.

عند استخدام التطبيق مع حسابات خارج فريق التطوير، استكمل ما تطلبه لوحة Meta من مراجعة صلاحيات والتحقق التجاري وروابط الخصوصية وحذف البيانات. نطاق الطلب والموافقة يتحدد حسب المنتج والحساب؛ لم يُفحص حسابك في هذه المراجعة. مراجع: [WhatsApp Cloud API](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started) و[نشر صفحات فيسبوك](https://developers.facebook.com/docs/pages-api/posts/). لم تُجلب هاتان الصفحتان بنجاح أثناء الفحص الآلي؛ النقص المذكور مثبت أيضًا في كود المشروع.

### 6.4 واتساب بالتحديد

1. داخل تطبيق Meta جهّز منتج WhatsApp والرقم التجاري وحساب الأعمال. سجّل `WHATSAPP_PHONE_NUMBER_ID` و`WHATSAPP_BUSINESS_ACCOUNT_ID` إذا لم يُكتشفا؛ هذان معرفان مختلفان عن رقم الهاتف المكتوب بصيغته العادية.
2. طريق OAuth يستخدم ربط Meta. يوجد بديل static عبر `WHATSAPP_ACCESS_TOKEN` للاستخدام الذي يناسب حسابك، لكنه يتطلب إدارة صلاحية الرمز يدويًا. اختبر دائمًا أن الرمز يملك وصولًا لرقم WhatsApp نفسه؛ وصوله لصفحة فيسبوك لا يثبت ذلك.
3. افتح صفحة واتساب في الموقع، ثم اختبر الاتصال وزامن القوالب. راجع الحالة واللغة واسم القالب من Meta.
4. اضبط Webhook على `/api/webhooks/meta/whatsapp` مع الاشتراك في `messages` حسب إعداد حساب الأعمال.
5. اختبر رسالة واردة من رقم تجريبي مصرح به، ثم ردًا ضمن نافذة الخدمة، ثم قالبًا معتمدًا خارجها. الكود يفرض قالبًا خارج نافذة 24 ساعة ويفحص الانسحاب.
6. اختبر إلغاء الاشتراك والتسليم وتكرار الحدث. ابدأ حملة بـ`dryRun` ومعاينة عدد المؤهلين؛ الحد الحالي 50 مستلمًا في الدفعة.

**نقطة تحقق مهمة:** اكتشاف حساب واتساب في OAuth مشروط حاليًا بوجود صفحة، واختيار الأصول آلي لأول النتائج. كذلك يجب التأكد أن الرقم/الأصل محفوظ في بيانات الاتصال التي يستخدمها محلل توجيه Webhook للمساحة؛ مجرد ضبط متغيرات static لا يثبت استقبالًا صحيحًا في بيئة متعددة العملاء.

في الدالة `connectedWhatsAppPhoneNumberId` يأخذ `WHATSAPP_PHONE_NUMBER_ID` العام أولوية على الرقم المحفوظ للمساحة. لا تستخدم رقمًا عامًا مشتركًا عند تجهيز أرقام مختلفة لعدة عملاء؛ يلزم تفضيل هوية الاتصال المعين والتحقق من تطابق الرقم والرمز والمساحة في جميع المسارات قبل هذا النوع من الإطلاق.

### 6.5 Microsoft 365: البريد والتقويم

1. افتح Entra ثم App registrations، وسجّل تطبيق Web. اختر نوع الحسابات المطابق لعملائك واضبط عنوان العودة.
2. انسخ Client ID و**قيمة** Client Secret، وليس معرف السر، وحدد Tenant ID المناسب.
3. الصلاحيات المفوضة في الكود: `offline_access` و`User.Read` و`Mail.Read` و`Mail.Send`. للتقويم أضف `Calendars.Read` و`Calendars.ReadWrite` واضبط `MICROSOFT_ENABLE_CALENDAR=true` قبل إعادة التفويض.
4. اضبط متغيرات القسم 8 ثم ابدأ الربط، واختبر بريد الحساب المتصل.
5. لتفعيل الاستقبال استدعِ `POST /api/integrations/microsoft/subscribe` من إجراء مصادق عليه كمالك، بعد أن يصبح مسار `/api/webhooks/microsoft/mail` متاحًا للعامة عبر HTTPS. الاشتراك يحتاج التجديد؛ يوجد تجديد في المجدول الداخلي، لذلك يجب بقاء العملية عاملة.
6. اختبر بريدًا واردًا، ثم إرسالًا مصرحًا به، ثم قراءة موعد وإنشاء موعد تجريبي إذا فعّلت التقويم.

المسار يستخدم اسم `microsoft`، بينما معرف المزود داخل التعيينات هو `microsoft365`. بريد العملاء عبر Microsoft مستقل عن بريد التحقق والدعوات الذي ترسله منصة HyperCool. مرجع [تسجيل التطبيق في Entra](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app) و[صلاحيات Graph](https://learn.microsoft.com/en-us/graph/permissions-overview).

### 6.6 X

1. أنشئ تطبيق OAuth 2.0 مناسبًا لخادم Web، وجهّز Client ID وClient Secret وعنوان العودة، وتأكد من وصول حسابك للعمليات المطلوبة وحدود الاستخدام.
2. **أصلح أولًا:** الكود يطلب `offline_access` بينما الاسم الرسمي في X هو `offline.access`. هذا تعديل كود وليس متغير بيئة.
3. الصلاحيات المطلوبة بعد الإصلاح: `tweet.read` و`tweet.write` و`users.read` و`offline.access`؛ PKCE موجود في الموصل.
4. ابدأ OAuth من الموقع ثم اختبر الحساب وتجديد الرمز ونشر عنصر معتمد. راجع استخدام نطاقات X الحالية في الموصل؛ توجد عناوين `twitter.com` قديمة تستلزم تجربة فعلية.

`X_BEARER_TOKEN` الخاص بالتطبيق لا يحل محل تفويض المستخدم للنشر. استخدم `SOCIAL_PUBLISHING_TEST_MODE=true` للتدريب المحلي على مسار X/LinkedIn؛ هذه ليست تجربة نشر حقيقية ولا تؤثر على Meta. المرجع الرسمي الذي يثبت اسم الصلاحية: [OAuth 2.0 مع PKCE لدى X](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code).

### 6.7 LinkedIn

1. أنشئ تطبيقًا مرتبطًا بصفحة الشركة، وحدد Client ID وSecret وRedirect URI.
2. فعّل منتجات الهوية والوصول اللازمة، واطلب Community Management حسب ما تسمح به لوحة حسابك. الكود يطلب `openid profile email w_organization_social r_organization_social rw_organization_admin`.
3. لا تبدأ التفويض بمجموعة صلاحيات غير معتمدة؛ الكود يطلب المجموعة دفعة واحدة، وقد يرفض المزود شاشة الموافقة نفسها. نجاح تسجيل الهوية لا يثبت أهلية نشر صفحة شركة.
4. اربط الحساب الذي يملك صلاحية إدارة الصفحة، ثم تحقق من Organization ID واختبر النشر المعتمد وتجديد الاتصال.

التنفيذ يستهدف صفحات الشركات، وليس الحساب الشخصي. راجع توافق مسارات وإصدارات LinkedIn المستخدمة مع المنتجات المعتمدة لحسابك قبل الاعتماد عليها إنتاجيًا. المرجع: [Community Management](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/community-management-overview).

### 6.8 زد

اضبط `ZID_CLIENT_ID` و`ZID_CLIENT_SECRET` و`ZID_REDIRECT_URI`؛ الأخير هو المسار العام `/api/integrations/oauth/zid/callback`. أضف متجرًا من مركز الربط ثم اختبر هويته.

العمليات المنفذة: `get_orders` و`get_customers` للقراءة. اربط أداة الوكيل بالاتصال ذي القدرة `commerce.orders.read` أو `commerce.customers.read`. قراءة المنتجات والمخزون والكتابة وWebhooks غير منفذة في موصل زد الحالي. لا تفترض أن أداة منتجات سلة ستعمل على زد.

الوثيقة المحلية تصرح بأن اختبارات الموصل تعتمد محاكاة العقد ولم توثق اختبارًا حيًا؛ لم يُنفذ اختبار حي في هذه المراجعة كذلك. جرّب OAuth وجلب طلب/عميل وتجديد الرمز من متجر تجريبي قبل تفعيله لعميل حقيقي. المرجع: [تفويض زد](https://docs.zid.sa/authorization).

### 6.9 بريد المنصة عبر Resend

أضف نطاق بريد تملكه، وانسخ سجلات التوثيق من لوحة Resend إلى DNS حتى تصبح حالة النطاق موثّقة، ثم جهّز `PLATFORM_RESEND_API_KEY` و`PLATFORM_MAIL_FROM`. عنوان المرسل يجب أن ينتمي للنطاق الموثّق. اختبر وصول رسالة تحقق ودعوة واستعادة كلمة مرور، وروابطها يجب أن تستخدم `PUBLIC_ORIGIN` الصحيح.

اترك `PLATFORM_MAIL_TRANSPORT` فارغًا في الإنتاج؛ قيمة `capture` مخصصة للاختبار وتخزن الرسائل بدل إرسالها. المرجع: [توثيق نطاقات Resend](https://resend.com/docs/dashboard/domains/introduction).

### 6.10 Turnstile والتسجيل العام

يوجد تحقق خلفي باستخدام `CAPTCHA_PROVIDER=turnstile` و`TURNSTILE_SECRET_KEY`. لكن البحث في الواجهة الحالية لم يجد عنصر Turnstile أو تمرير `captchaToken` في نماذجها. لذلك تشغيل الإلزام على واجهة التسجيل الحالية قد يجعل التسجيل يُرفض.

قبل فتح التسجيل العام: أضف widget باستخدام Site Key، ومرر الرمز للخادم واختبر النجاح والفشل وانتهاء صلاحية التحدي على الدومين الحقيقي. لا يوجد متغير Site Key مدمج تلقائيًا في النسخة الحالية؛ يلزم استكمال الواجهة. إلى ذلك الحين يمكن إطلاق تجربة بالدعوات مع `ALLOW_PUBLIC_SIGNUP=false`. المرجع: [بدء Turnstile](https://developers.cloudflare.com/turnstile/get-started/).

### 6.11 شات الموقع والأتمتة والموصلات الإضافية

**الشات:** صفحة التسويق ← إعداد الشات. حدد النطاقات المسموح بها ورسالة الترحيب وساعات العمل، ثم انسخ كود التضمين الذي يولده الموقع وفيه `widget-embed.js` و`data-widget-id`. الصقه في موقعك المقصود فقط، واختبر إنشاء المحادثة في CRM واستجابة وكيل المبيعات. لا تستخدم معرفًا تخمينيًا.

**الأتمتة:** جهّز الاتصالات أولًا، ثم أنشئ Workflow كمسودة، وافحص Trigger والخطوات والأدوات. التفعيل والتنفيذ المباشر لهما موافقات وجاهزية؛ اختبار الوكلاء منفردين لا يضمن نجاح سير العمل كله.

**المحاسبة أو خدمات أخرى:** أداة `get_invoices` عامة وتحتاج موصلًا منشورًا فعليًا بقدرة `accounting.invoices.read`. لا يوجد ربط جاهز بكل برنامج محاسبة لمجرد وجود الأداة. يدعم المشروع Generic REST/OAuth2/Webhooks، لكن يجب تعريف واجهات المزود والصلاحيات وتحويل البيانات وتجربتها ثم النشر عبر الحوكمة. لا تستخدم موصلات الأمثلة مثل `acme` باعتبارها خدمات تجارية جاهزة.

المسار `/srv/hypercool-data` مثال Linux؛ على Windows استخدم مسارًا دائمًا بصلاحيات مناسبة. ولإنشاء مفتاح تشفير مرة واحدة على جهاز موثوق:


احفظ الناتج سرًا. احتفظ بنسخة آمنة منه مع خطة الاستعادة؛ تغيير المفتاح اعتباطيًا يفقدك القدرة على فك أسرار الاتصالات القديمة.

## 9. خطة النشر العملية

### قبل رفع الموقع

1. اختر نسخة `_public-site-worktree` المقصودة، وراجع تغييراتها وملفاتها الضرورية. لا ترفع النسخة الأخرى بالخطأ ولا تضع مجلد العمل كله داخل مجلد يخدمه Apache كملفات عامة.
2. استخدم بيئة تدعم Node.js بإصدار يحقق `package.json` الحالي، وهو `>=24.11.0`، مع `node:sqlite` وعملية طويلة التشغيل وتخزين دائم. XAMPP/PHP وحدهما لا يشغلان هذا التطبيق.
3. اضبط DNS وHTTPS وReverse proxy إلى منفذ Node. اربط `PUBLIC_ORIGIN` بالأصل الدقيق دون مسار فرعي، وسجّل عناوين العودة المطابقة في المزودين.
4. أنشئ مجلد بيانات دائمًا خارج إصدار النشر، واضبط صلاحياته والنسخ الاحتياطي.
5. جهّز الحساب الإداري والتشفير وبريد المنصة ومزود AI. لا تعتمد على SQLite داخل نظام ملفات مؤقت أو نشر واجهة static فقط.

### أوامر التحقق والتشغيل

نفّذ من جذر نسخة النشر الصحيحة:

```bash
npm ci
npm run build
npm test
npm run production:check
npm start
```

`build` هنا فحص صياغة لمداخل الخادم وليس حزمة واجهة مبنية. الاختبارات الكاملة لم تُشغّل أثناء إعداد هذا التقرير؛ لا تعتبر إدراج الأمر نتيجة نجاح. تشغيل `production:check` في هذه المراجعة فشل بالموانع الثلاثة الموضحة أعلاه.

شغّل التطبيق بخدمة تستأنف تلقائيًا عند إعادة تشغيل الخادم، من خلال إدارة العمليات المتاحة في استضافتك. ابدأ **بنسخة عملية واحدة**؛ المجدول والقيود وبعض حالات OAuth تعتمد على العملية، ولا توجد هنا بنية Redis/طابور موزع كاملة تسمح بافتراض توسع أفقي آمن.

### بعد الرفع

1. افتح [فحص الحياة](https://app.example.com/health/live) و[فحص الجاهزية](https://app.example.com/health/ready). نجاح الجاهزية يثبت الأساس وقاعدة البيانات، وليس نجاح جميع التكاملات الاختيارية.
2. اختبر تسجيل الدخول والخروج واستعادة كلمة المرور واختيار المساحة وتقييد الأدوار.
3. اختبر كل قناة من المصدر إلى CRM ثم إلى الأداة/الوكيل وصولًا للنتيجة الخارجية.
4. اختبر توقف وإعادة تشغيل العملية وبقاء البيانات والمجدول وصلاحية الجلسات وفق السلوك المقصود.
5. فعّل النشر والإرسال تدريجيًا بعد نجاح الاختبارات. مفاتيح الإرسال والنشر الافتراضية الأربعة مفعلة إذا تُركت فارغة؛ لهذا يحتوي نموذج البداية على `false` صريحة.

### النسخ الاحتياطي والاستعادة

```bash
npm run backup
node scripts/backup.mjs <dataDir> <backupDir>
node scripts/restore.mjs <backup-file> <isolated-restore-test-dir>
```

اختبر الاستعادة أولًا في مجلد اختبار معزول. أداة النسخ تستخدم SQLite بطريقة مناسبة للنسخ، فلا تعتمد على نسخ ملف قاعدة البيانات منفردًا أثناء الكتابة. جدولة النسخ اليومية مسؤولية تشغيلية؛ وجود السكربت لا يعني أنه يعمل تلقائيًا. احتفظ بنسخة خارج الخادم وبمفتاح التشفير في مكان آمن منفصل. جهّز أيضًا خطة رجوع لإصدار التطبيق السابق.

| قبل التوسع | معماري | عملية واحدة ومجدول داخلها وغياب طابور موزع كامل | قياس حمل، قفل مشترك وجدولة/طابور مناسب قبل تعدد النسخ |
| تحسين تشغيلي | توثيق | بعض وثائق setup و`.env.example` أقدم من المزايا الحالية | تحديثها من الكود وعدم استخدام أرقام الأدوات/الوكلاء القديمة |

**يمكن إطلاق تجربة محدودة** بعد معالجة الموانع الأساسية واختبار القنوات المختارة، مع تعطيل/عدم تقديم الميزات غير المنفذة. لا يلزم انتظار Canva أو زد إذا لم يكونا ضمن نطاق الإطلاق. أما الوعد بأن «كل الوكلاء وكل القنوات تعمل بالكامل» فلا تدعمه الحالة الحالية قبل معالجة البنود المرتبطة بها.

## 13. مرجع فني للمطور

المسارات التالية موجودة في `src/application.js`. طلبات الإدارة تتطلب جلسة ودورًا مناسبًا وضوابط الطلب المعتادة؛ ليست روابط عامة لفتحها وإجراء التعديل بلا مصادقة.

| العملية | المسار |
|---|---|
| إعداد وكيل | `GET /api/agents/{agentId}/config` و`PATCH /api/agents/{agentId}/config` |
| مزود/نموذج الوكيل في المسار القديم | `POST /api/agents/{agentId}/model-config` |
| أدوات وكيل | `GET /api/agents/{agentId}/tools` |
| تعيين اتصال أداة | `PUT /api/agents/{agentId}/tools/{toolSlug}` |
| جاهزية وكيل | `GET /api/agents/{agentId}/readiness` |
| خريطة الربط | `GET /api/agent-connection-map` |
| اختيار الاتصالات الملائمة | `GET /api/tools/{toolSlug}/connections` |
| اختبار اتصال مخزن | `POST /api/integrations/connections/{id}/test` |
| تدوير مفتاح AI لاتصال | `PUT /api/integrations/connections/{id}/credential` |
| اشتراك البريد الوارد | `POST /api/integrations/microsoft/subscribe` |
| مزامنة القوالب | `POST /api/whatsapp/templates/sync` |
| مزامنة التحليلات | `POST /api/marketing/analytics/sync` |

مثال هيكل تعيين AI للوكيل، بمعرف اتصال حقيقي من نفس المساحة ونموذج اختبرته:

```json
{
  "enabled": true,
  "aiConnectionId": "REPLACE_WITH_CONNECTION_ID",
  "model": "REPLACE_WITH_TESTED_MODEL"
}
```

ومثال تعيين أداة بعد التحقق من التوافق:

```json
{
  "enabled": true,
  "connectionId": "REPLACE_WITH_COMPATIBLE_CONNECTION_ID"
}
```

### مصادر المراجعة داخل المشروع

`src/domain.js` لحصر الوكلاء؛ `src/runtime/tools.js` لجرد الأدوات الفعلي؛ `agent-readiness.js` للأدوات المطلوبة والاختيارية؛ `agent-config.js` و`tool-assignments.js` للتعيينات؛ `permissions.js` لسقف الصلاحيات؛ ملفات `*-oauth.js` لمسارات وصلاحيات المزودين؛ `capability-map.js` لفحص القدرات؛ `meta-publishing.js` لخرائط التحليلات؛ `src/application.js` للمسارات؛ `scripts/production-check.mjs` لفحص الإعداد؛ `public/pages/marketing.js` لإعداد الشات؛ `public/pages/control-center.js` لإضافة الاتصالات.

المصادر الخارجية موضوعة بجوار إرشادات كل خدمة. أُدرجت روابط لوحات الحسابات لتبدأ التنفيذ، لكن صلاحيات حساباتك واعتماد تطبيقاتك والإرسال الحقيقي لم تختبر ضمن إعداد الملف. أسعار الخدمات وتوفر النماذج تحددها لوحات المزودين عند الربط، ولم تُوضع أسعار أو وعود موافقة غير متحققة.
