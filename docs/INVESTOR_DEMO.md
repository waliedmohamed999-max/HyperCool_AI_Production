# Investor Demo Data Pack

Two realistic, clearly-labeled DEMO tenants — **Nova Store** (E-commerce) and **Vertex
Solutions** (B2B Services) — seeded into the real local database using this app's own real
create/write functions, for use in an investor presentation. Every number and record is
generated by a deterministic, seeded script (`scripts/demo-seed.mjs`); nothing is hand-typed
into the UI, and nothing ever leaves this machine (zero outbound network calls, zero real
credentials, zero real messages/publishes).

## Quick start

```bash
# 1. Set a real password for the shared investor login (never commit this value)
export DEMO_USER_PASSWORD="choose-a-strong-passphrase-here"

# 2. Seed both demo tenants (safe to re-run — it skips a tenant that already exists)
npm run demo:seed

# 3. Check what's there
npm run demo:status

# 4. Start the app as usual and log in with username `investor_demo`
npm start
```

To wipe the demo and start over:

```bash
npm run demo:reset   # removes ONLY the two demo tenants + investor_demo — nothing else
npm run demo:seed    # reseed — produces the EXACT same data every time (fixed random seed)
```

## A. Demo architecture

- `scripts/demo/shared.mjs` — shared helpers: a deterministic seeded PRNG (`mulberry32`, seed
  string `"hypercool-investor-demo-v1"` — the same seed always produces the same sequence, so
  `demo:reset && demo:seed` is byte-for-byte reproducible), relative-date helpers (`daysAgoIso`,
  never a hardcoded calendar year), a `patchJsonRow` helper for the one legitimate case where a
  real create function hardcodes its own timestamp (see "Honest limitations" below), and the
  Arabic name/product/client-name pools.
- `scripts/demo-seed.mjs` — the real seeder. Calls `createApp({env: process.env})` (the exact
  same bootstrap the production server uses — every table/migration runs identically) and then
  calls this codebase's own real functions directly: `createTenant`, `auth.createUser`,
  `createConnection`/`updateConnection`, `replaceProducts`, `createLead`/`updateLead`,
  `createContent`/`reviewContent`/`approveContent` + `insertContent`/`writeContent`,
  `createApproval`/`decideApproval`, `createEscalation`, `updateTenantAgentConfig`,
  `setAutonomy`, `recordAudit`, `saveDailyBrief`, `saveWeeklyReport`. It never opens an HTTP
  server and never starts the scheduler — it is a pure, one-shot data seeder.
- `scripts/demo-reset.mjs` — deletes every row scoped to the two demo tenants' `tenant_id`
  (found by their fixed slugs, never by name/heuristic), then the tenant rows themselves, then
  the `investor_demo` user (only once it has zero remaining memberships anywhere — a real
  safety check). Refuses to touch a tenant at either demo slug unless it is genuinely marked
  with the demo pack's own marker (defense in depth against a hypothetical slug collision).
- `scripts/demo-status.mjs` — read-only. Prints real record counts per tenant, or "NOT SEEDED".

## B. Seed command

```bash
DEMO_USER_PASSWORD="..." npm run demo:seed
```
Idempotent (Part 36): if Nova Store or Vertex Solutions already exists (checked by its own
fixed slug), that tenant is skipped entirely and logged as "already seeded" — running the
command twice never creates a duplicate. Each tenant is seeded independently, so if only one
was previously reset, running seed again only recreates that one.

## C. Reset command

```bash
npm run demo:reset
```
Removes ONLY: the `nova-store-demo` and `vertex-solutions-demo` tenants and every row scoped to
their `tenant_id` (CRM leads/messages/followups, content, connections, products, approvals,
escalations, agent configs/autonomy, audit logs, daily briefs, weekly reports, memberships), and
the `investor_demo` user (only if it has no memberships left anywhere else). **Never** touches
any other tenant, user, or table — proven by a dedicated test
(`tests/demo-seed.test.js`) that seeds a real, unrelated tenant in the same database first and
asserts it survives a full `demo:reset` untouched.

## D. Status command

```bash
npm run demo:status
```
Prints, per tenant (or `NOT SEEDED`): tenant id, status, whether the demo marker is present, and
real row counts for members/CRM leads/content/connections/products/approvals/escalations
("tasks")/agent configs/audit entries/daily briefs/weekly reports. Also reports whether the
`investor_demo` account exists. Read-only — never writes anything.

## E. Production guard

`demo-seed.mjs` refuses to run when `NODE_ENV=production` **unless** `ALLOW_DEMO_SEED=true` is
set explicitly:
```bash
NODE_ENV=production node scripts/demo-seed.mjs
# [demo:seed] Refusing to run: NODE_ENV=production and ALLOW_DEMO_SEED is not "true".

NODE_ENV=production ALLOW_DEMO_SEED=true DEMO_USER_PASSWORD="..." node scripts/demo-seed.mjs
# proceeds
```
Outside `NODE_ENV=production` (local/dev/staging), the script runs freely — this guard exists
specifically to stop an accidental `npm run demo:seed` against a real production deployment.

## F. Demo user

Username: **`investor_demo`**. Password: whatever you set in `DEMO_USER_PASSWORD` at seed
time — **never hardcoded, never committed**. The account is added as an **owner** member of
both Nova Store and Vertex Solutions, so logging in once lets you switch freely between both
tenants via the workspace switcher (no separate login per company). If `DEMO_USER_PASSWORD` is
missing or shorter than 12 characters, the seed script refuses to run rather than fall back to a
weak default.

## I. Record counts

Run `npm run demo:status` for the live, authoritative counts. Approximate totals across both
tenants: ~14 team users, ~9 connections, 18 products, ~155 CRM leads, ~32 content items, ~18
approvals, ~80 task-equivalent escalations, 24 agent configs, ~95 narrative activity entries (plus
every real action's own audit trail — several hundred more rows in total), 2 daily briefs, 8
weekly reports. Comfortably within "hundreds to low thousands, not millions" (Part 46) — a full
`demo:seed` run completes in a few seconds with zero network calls.

## J. Reports populated

Both tenants get a real, freshly-computed **latest Daily Brief** (`saveDailyBrief`) and **4 real
Weekly Reports** (`saveWeeklyReport`, most recent 4 Sundays) — every number in them is derived
from the actual seeded CRM/content/approval/escalation rows by the app's own existing report
builders (`buildBrief`/`buildWeeklyReport`/`buildExecutiveReport`), never hand-typed.

## K. Agents populated

All 12 real agents (`frost, strategy, copy, creative, compliance, publishing, leads, sales,
followup, intelligence, performance, memory`) get a real `tenant_agent_configs` row
(enabled + a model reference) for both tenants. Nova promotes `sales` (its conversation agent)
to autonomy level L1; Vertex promotes `leads` and `followup` to L1 — matching each company's
"strongest agents" from the spec.

## L. Integrations populated

Real `integration_connections` rows with a genuine MIX of health states (never all green) —
CONNECTED, DEGRADED, and TOKEN_EXPIRED (shown as "needs reauthorization" in the UI) — so the
Readiness/Health views look like a real, lived-in system. **No credential is ever stored** for
any demo connection (the seed script never calls `storeCredential`/the Vault at all) — there is
no fake encrypted secret anywhere.

## M. CRM populated

Real `crm_leads` rows via the actual `createLead`/`updateLead` functions — every validation rule
in the real CRM module ran for real during seeding (email/phone format, stage transitions,
required reasons, optimistic-concurrency versioning). Creation/update timestamps are then spread
across the last 90 days (see "Honest limitations" — these two functions hardcode "now"
internally, so the seed script patches just the timestamp field in the row's own JSON afterward,
never touching any other field).

## N. Tasks populated

**Mapped to `agent_escalations` — see the honest note below.** There is no separate Tasks table
in this codebase; the app's own `runtime/escalations.js` explicitly says an escalation IS the
task ("someone must act"). 35 (Nova) / 45 (Vertex) escalations were seeded across P0-P5
priorities and department-flavored reasons (Marketing/Operations/Support/Content/Sales for Nova;
Sales/Operations/Client Success/Management/Marketing for Vertex), roughly half already resolved.

## O. Approvals populated

Real `agent_approvals` rows via `createApproval`/`decideApproval`, using the app's own real
action-type enum (`discount`, `publish_content`, `send_marketing_message`, `large_quote`,
`connector_action`), with a real mix of PENDING/APPROVED/REJECTED outcomes.

## P. Automation populated

**No dedicated "workflow" entity exists in this codebase** (see honest note). What's real and
was populated: the historical activity/audit trail (narrative entries like "detected low
inventory", "recommended budget shift", "flagged high-risk client") and the pending-followup
concept that does exist (`crm_followups` — not separately seeded with history since the real
`createFollowups` function requires a real future `startAt`, i.e. it is inherently forward-
looking, not backdatable).

## Q. Activity/audit populated

Every real seed action's own audit trail (`CRM_LEAD_CREATED`, `WEEKLY_REPORT_CREATED`, etc. —
timestamped "now", the moment you actually ran the seed) plus 55 (Nova) / 40 (Vertex) explicitly
backdated narrative entries spread across the last 90 days, giving the Audit Trail page real
depth without pretending an AI model actually ran 90 days ago.

## R. Workspace switch verified

`tests/e2e/investor-demo-journey.e2e.mjs` logs in as `investor_demo`, picks Nova Store from the
real workspace-selection gate, visits 9 real pages, switches to Vertex Solutions through the
real header workspace switcher, and re-visits the same pages — confirming no stale data survives
the switch (every page re-fetches from the newly active tenant).

## S. Tenant isolation verified

Two layers of proof: (1) `tests/demo-seed.test.js` queries the raw database directly and asserts
zero Nova lead ids ever resolve under the Vertex tenant scope; (2) the E2E journey asserts the
Vertex dashboard text never contains Nova's company name or product names after switching. Both
tenants exist in the exact same real multi-tenant database, isolated by the app's own
already-battle-tested `tenant_id` scoping — no special-cased "demo isolation" logic was added.

## T. No-external-call guarantee

The seed script never imports or calls anything capable of an outbound request: no
`agentRuntime.run` (no LLM call), no `storeCredential` (no OAuth exchange, no secret at rest),
no `fetch(`, no `sendTestWebhookEvent`/`processGenericWebhook` (no webhook delivery). Enforced by
a structural test (`tests/demo-seed.test.js`'s last test) that fails the build if any of those
ever gets referenced in `demo-seed.mjs` again in the future.

## Honest mapping — what's real vs. what has no backing entity in this codebase

Several concepts in a typical "investor demo" checklist simply do not exist as their own
feature in HyperCool today. Rather than inventing new database tables/API routes/UI screens for
a demo (a much larger undertaking than seeding data — and dead schema nobody could see would be
worse than nothing), this data pack uses the closest REAL existing mechanism and documents the
substitution honestly here:

| Requested concept | Real substitute used | Why |
|---|---|---|
| **Tasks board** (Backlog/In Progress/Review/Done/Blocked) | `agent_escalations` (P0-P5, OPEN/RESOLVED) | No Tasks table exists; `runtime/escalations.js` is this app's own documented "task" equivalent ("an escalation IS the task") |
| **Campaigns / spend / impressions / CTR / ROAS** | Campaign-themed `content_items` (title/body only) | No campaigns table or ad-metrics field exists anywhere in this codebase |
| **Orders (~1,200) / Revenue (~280,000 SAR) / AOV / conversion % / repeat-customer %** | Not fabricated as standalone numbers | No orders/customers table exists (Zid's `get_orders`/`get_customers` are LIVE remote reads, never persisted locally); inventing a parallel numeric field with no display surface would be dishonest padding, not a real KPI |
| **Customer segments (VIP/Repeat/New/At Risk)** | Not modeled | No such field/computation exists on any lead/customer record |
| **"Clients" as a distinct entity from leads** (Vertex) | WON-stage B2B `crm_leads` | The CRM has no separate clients table; a won B2B lead is the closest real analogue |
| **Projects / client work** (Vertex) | Not modeled | No projects/work-items table exists |
| **TikTok / Snapchat content channels** | Not used — real channels only (Instagram/Facebook/X/LinkedIn) | `createContent`'s own validation hard-rejects any other platform string |
| **Named workflow automations** ("New Lead Follow-up", "Proposal Reminder", …) | Narrative `audit_logs` entries | No generic workflow-definition/execution-history entity exists; the real automation-ish primitives are the scheduler (cron-like, not user-facing) and `crm_followups` (inherently forward-dated, can't represent history) |
| **Sales-call / meeting calendar** | Not modeled — the real Calendar (`#planning`) is content scheduling only | No separate meetings/events table exists locally (Microsoft 365's calendar tools are live-remote-only) |
| **"Email" as a Vertex integration** | Microsoft 365 (real mail + calendar) | No standalone "Email" integration definition exists; Microsoft 365 is the closest real substitute |
| **Team workload dashboard** (one overloaded, one balanced, one light) | Not built as a dedicated view | `team-ops.js`'s existing dashboard has no per-tenant filter at all today (a pre-existing gap, unrelated to this demo pack — flagged here for visibility, not fixed as part of this task) |

This mapping was an explicit, agreed decision (not a unilateral judgment call) — see the
project's own conversation history for the exact question asked and the answer given before any
of this was built.
