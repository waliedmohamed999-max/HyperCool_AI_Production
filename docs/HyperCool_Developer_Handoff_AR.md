# HyperCool — تقرير التسليم الفني الشامل للمبرمج

**تاريخ المراجعة: 10 سبتمبر 2026 — إصدار التقرير 1.0**

**المشروع:** HyperCool AI CMO & Sales Operating System. **مجلد العمل:** `E:\xampp\HyperCool_AI_Production`. **إصدار package.json:** `0.5.0`.

هذا التقرير يصف الملفات الموجودة وقت المراجعة، ويقارنها بالنطاق المطلوب. لا يفترض أن كل بطاقة في الواجهة تمثل تكاملًا عاملًا. لم تُقرأ مفاتيح `.env` أو تُنسخ بيانات العملاء أو كلمات المرور إلى التقرير. أسماء المتغيرات أدناه أسماء إعدادات فقط. لا توجد هنا شهادة بإتمام اتصال حي بحسابات المنصات.

الأسماء التجارية وروابط المنصات الواردة في مستند النطاق مرجع متطلبات، وليست نتيجة تحقق خارجي جديد. التقرير ليس سجل commits؛ لا يمكن نسب كل تعديل إلى شخص أو توقيت دون تاريخ مستودع موثق. تقرير الواجهة السابق يوثق مرحلة سابقة؛ أضيفت بعدها وحدات محتوى وذاكرة وتكاملات وفريق أحدث، وتشملها هذه النسخة.

## 1. الملخص التنفيذي

المنصة حاليًا تطبيق تشغيل محلي ذو واجهة عربية ومصادقة وقاعدة بيانات ومجموعة خدمات أعمال فعلية. تدير المسودات والمراجعة والاعتماد والتقويم وCRM والذاكرة والتقارير، وبها محرك موحد لتشغيل 12 وكيلًا. ليست مجرد صفحات تصميم، وليست بعد منصة تسويق ومبيعات مستقلة مكتملة تعمل على جميع القنوات الخارجية.

يوجد كود اتصال حقيقي بـAnthropic للتوليد والامتثال والمحرك، وكود لاستيراد منتجات سلة. أما إرسال واتساب والبريد والنشر الاجتماعي وتوليد التصميمات ومزامنة الطلبات، فأدواتها الحالية تعيد حالة صريحة بأن التكامل مطلوب. **وضع token لهذه الأدوات لا يحولها تلقائيًا إلى موصل عامل؛ يلزم بناء الكود أيضًا.**

الجدولة الداخلية موجودة فعلًا وتبدأ مع `npm start`. تنفيذ الاختبارات الحالية أثبت نجاح **145 اختبارًا**. اختبار رحلة الواجهة الأقدم توقف عند selector لزر ذاكرة تغير اسمه؛ لذلك لا يصح وصف اختبارات E2E الحالية بأنها كلها ناجحة اعتمادًا على تقرير سابق من 40 شاشة. فحص تسليم مستقل فتح الأربعين حالة عرض الحالية دون أخطاء JavaScript أو تجاوز أفقي، لكنه رصد ضعف تباين ألوان في كل الحالات؛ هذه ملاحظة قائمة في النسخة المفحوصة.

أهم أولويات المبرمج: تثبيت نسخة مرجعية واختبارات الواجهة، توحيد عقود وصلاحيات الوكلاء، معالجة ثغرات الربط بين الأهلية والتنفيذ، تأمين التشغيل المستضاف، ثم بناء موصل خارجي واحد كامل واختباره قبل توسيع القنوات.

لا تستخدم نسبة إجمالية مثل «المشروع 90%»؛ المتبقي يحتوي أعمالًا كبيرة مستقلة مثل القنوات وOAuth والبنية التشغيلية، وعدد الشاشات لا يقيس اكتمال المنتج.

## 4. المعمارية وكيف يمر الطلب

مسار الاستخدام البشري:

```text
Browser / index.html
  -> public/app.js + وحدات الصفحات
  -> fetch(JSON) + Cookie + X-CSRF-Token
  -> src/server.js: routing/auth/validation
  -> خدمة الأعمال: domain / crm / planning / knowledge / reporting
  -> SQLite + سجل العملية
  -> JSON response
  -> إعادة عرض البيانات والمكونات
```

مسار الوكيل:

```text
حدث CRM أو تشغيل يدوي أو Scheduler
  -> Frost / EventBus
  -> AgentRuntime
  -> Prompt + JSON Schema + أدوات مسموحة بالمستوى
  -> Anthropic tool-use loop
  -> إعادة فحص صلاحية كل أداة على الخادم
  -> تنفيذ محلي أو INTEGRATION_REQUIRED
  -> تحقق القرار النهائي + حفظ التشغيل والأدوات والتصعيد
```

`createApp({dataDir,env,fetcher})` نقطة الإنشاء المهمة. يسمح بحقن قاعدة مؤقتة ومزود fetch للاختبارات. لا يبدأ المؤقت بمجرد import؛ كتلة تشغيل `src/server.js` هي التي تستدعي `scheduler.start()`.

التطبيق single-process وsingle-workspace. لا يوجد tenantId أو عزل مؤسسات أو اشتراكات وفوترة SaaS. المظهر شبيه بمنصات SaaS، لكن المعمارية التشغيلية ليست منصة متعددة المستأجرين.

توجد معاملات `BEGIN IMMEDIATE/COMMIT/ROLLBACK` في `store.mutate`. لا تمر كل الكتابات عبرها؛ بعض خدمات Runtime والفريق تكتب مباشرة، ثم يضاف التدقيق في خطوة أخرى. هذا مهم عند تصميم atomicity عبر عدة جداول.

ترحيل `state.json` القديم يحدث مرة عند عدم وجود صف state؛ لا يُحذف الملف الأصلي، ويوسم المحتوى القديم `legacyUnauthenticated`. أعمدة الفريق أضيفت additive migrations، والسجلات القديمة قد تحمل تاريخ إنشاء/دخول NULL بدل اختلاق تواريخ.

WAL مهم للنسخ الاحتياطي: النسخ الخام لملف sqlite أثناء الكتابة ليس خطة backup معتمدة. يجب أن يضع المبرمج آلية SQLite backup متسقة أو إيقافًا منضبطًا ونسخة قابلة للاستعادة، مع اختبار restore. لا يوجد مدير migrations مرقم أو أداة backup/restore إنتاجية ضمن الملفات المفحوصة.

## 7. الحسابات والصلاحيات والأمان الموجود

ثلاثة أدوار فقط: owner وoperator وreviewer. أول استخدام ينشئ المالك دون كلمة مرور افتراضية. كلمة المرور 12–256 حرفًا، والاسم 100 حرف، وusername من 3–40 حرفًا إنجليزيًا/رقمًا/علامات مسموحة، ثم يُحفظ lowercase.

كلمات المرور salted scrypt. الجلسة عشوائية ويخزن hash الرمز في القاعدة، مدتها ثماني ساعات. Cookie اسمها `hc_session` مع HttpOnly وSameSite=Strict؛ لا Secure في إعداد localhost HTTP الحالي. المحاولات محدودة بعشر محاولات لكل IP ضمن 15 دقيقة، محفوظة في الذاكرة وتُصفّر بإعادة التشغيل. لا MFA ولا SSO ولا استعادة ذاتية بالبريد.

كل API محمي بعد setup/login/auth يتطلب جلسة، والكتابات تتطلب `X-CSRF-Token`. توجد قيود Host على localhost/127.0.0.1، والتحقق من Origin وsec-fetch-site، وحد جسم JSON 64KB، وnosniff، وCSP للملفات الثابتة.

| --- | --- | --- | --- |

| اعتماد محتوى | نعم | لا | لا |

| اعتماد/تجهيز المتابعات | نعم | لا | لا |
| إنشاء تقويم | نعم | نعم | لا |

**تفصيل مهم:** `/api/escalations/:id/resolve` لا يضيف authorize(owner) بعد حارس الجلسة العام؛ تقنيًا يمكن للأدوار الثلاثة استعماله، ولو كانت الواجهة تعرضه للمالك فقط. هذه فجوة سياسة/تنفيذ يجب حسمها، وليس كافيًا الاعتماد على إخفاء الزر.

إدارة الفريق الأحدث تشمل إنشاء عضو، تغيير دوره، إيقافه، إعادة تفعيله، حذفه، إعادة تعيين كلمة مروره بواسطة المالك، وإلغاء جلساته. توجد حماية من ترك النظام بلا مالك نشط. لا دعوات بريدية فعلية، ولا كلمات مرور مؤقتة بفرض تغيير عند أول دخول. وجود جلسة غير منتهية لا يثبت أن المستخدم متصل أو ينظر إلى الشاشة الآن.

المراجعة والاعتماد يمكن أن يجريهما نفس المالك؛ فصل الشخصين لم يُفرض في الكود.

## 8. المحتوى: الدورة المنفذة بالتفصيل

```text
DRAFT -> REVIEWED -> APPROVED
  تعديل -> نسخة جديدة DRAFT + الأصل SUPERSEDED
  رفض -> REJECTED
  تعديل/رفض النسخة القديمة -> إلغاء جدولة تلك النسخة
```

إنشاء المحتوى يقبل Instagram وFacebook وX وLinkedIn. العنوان حتى 200 حرف، النص العربي والإنجليزي حتى 10,000 لكل منهما. رابط المنتج يجب أن يكون HTTPS وعلى `hyper-cool.com` دون بيانات دخول في الرابط. الأصل البصري رابط HTTPS، وليس رفع ملف إلى التطبيق.

المراجع يسجل evidence ويؤكد facts/claims/link؛ وإذا وُجد أصل بصري يؤكد asset. الاسم والهوية الحقيقيان يؤخذان من الجلسة على الخادم. المراجعة تخزن SHA-256 لمحتوى يشمل العنوان والنصين والرابط والأصل والمنصة والتاريخ. الاعتماد يعيد فحص البصمة ويخزنها، فلا يُعاد استخدام اعتماد نص قد تغير.

التوليد من واجهة الكتابة يتطلب منتجًا مستوردًا معروضًا للبيع وبياناته أحدث من 24 ساعة، ونبرة علامة معتمدة، ومواصفة معتمدة مرتبطة بالمنتج. يمنع السياق التصريح بالأسعار والتوفر والادعاءات الطبية في هذا المسار. يدعم brief إضافيًا للحملة والجمهور والنوع واللغة والنبرة وCTA ومرحلة funnel وكلمات SEO والعرض والطول والمرجع، مع حدود طول.

`requestKey` والبصمة وصاحب الطلب تمنع تكرار نفس العملية أو استخدام المفتاح لطلب مختلف. التوليد المباشر يسمح بطلب نشط واحد في العملية. الطلبات RUNNING عند إعادة التشغيل تُوسم INTERRUPTED بدل إعادة دفع استدعاء مدفوع تلقائيًا. يعاد فحص السياق بعد رجوع النموذج قبل إنشاء المسودة.

الفحص الآلي للامتثال مسار مستقل مقيد بـDRAFT وبصمة وطلب وهوية. يعرض تصنيفًا ومشكلات وتصحيحات/أدلة مطلوبة. هو مساعد للمراجع وليس آلة لإثبات حقيقة الادعاء أو بديلًا عن اعتماد الإنسان.

مركز المحتوى الأحدث يعرض KPIs، pipeline مبنيًا على الحالات الحقيقية، مكتبة المحتوى، ملاحظات امتثال مصنفة، وملاحظات Frost بقواعد حسابية. الحالة SCHEDULED مشتقة من schedule_jobs؛ ليست حالة أصلية جديدة داخل المحتوى. لا يوجد PUBLISHED فعلي أو campaign entity مستقل حتى لو كان هناك حقل brief اسمه campaign.

## 9. التقويم والجدولة والمحفز الخارجي الاختياري

إنشاء التقويم يبني 30 يومًا بقواعد ثابتة: Instagram/X/Facebook يوميًا، وLinkedIn الأحد والثلاثاء والخميس. لا يولد ذلك 30 منشورًا ولا تصميمًا تلقائيًا، بل خانات وأفكار/محاور. قيد date/platform يمنع التكرار عند تداخل التقويمات.

الجدولة تتطلب اعتمادًا ومراجعة موثقين وبصمة مطابقة، موعدًا مستقبليًا بمنطقة زمنية، وتوافق تاريخ الرياض مع تاريخ المحتوى. LinkedIn يتطلب النص الإنجليزي واليوم المسموح؛ Instagram يتطلب أصلًا بصريًا. لا توجد خانة ثانية لنفس المنصة واليوم في هذا النموذج.

الحالات: SCHEDULED ثم READY_FOR_CONNECTOR أو BLOCKED، مع CANCELLED عند الإلغاء. لحظة الاستحقاق يعاد فحص الاعتماد. **READY_FOR_CONNECTOR لا يعني نُشر ولا أُرسل.** يوجد idempotencyKey، لكنه ليس بمفرده ضمان إرسال خارجي مرة واحدة؛ ذلك يتطلب تنفيذ connector وتسوية مع مزوده.

الحزمة اليومية لقطة واحدة لكل يوم، تحتوي قرارات ومحتوى الغد والفجوات والجدولة الموقوفة. لا ترسل تلقائيًا إلى البريد أو واتساب. التقرير الأسبوعي لقطة واحدة لكل أسبوع.

المجدول الداخلي يفحص كل 300,000ms افتراضيًا. ينشئ الحزمة أثناء الساعة 08 بتوقيت الرياض، ويحاول حفظ التقرير يوم الأحد، ويفحص فجوات المتابعة كل tick. يبدأ بعد أول interval، وليس cron عند الثانية 00 بالضبط. `run-now` يستدعي tick نفسه؛ خارج الساعة 08 لا يفرض إنشاء الحزمة اليومية.

نقطتا نهاية HTTP اختياريتان (`/api/automation/daily-brief`, `/api/automation/prepare-due`) بمفتاح `X-HyperCool-Token` متاحتان كمحفز خارجي احتياطي فقط — لبيئات استضافة لا تضمن بقاء عملية Node حية باستمرار لتشغيل الجدولة الداخلية بمفردها. أي مستدعٍ HTTP يعمل (cron، Windows Task Scheduler، أو أي أداة عامة)؛ لا يوجد اعتماد على أي منتج أتمتة بعينه. يجب أن يعمل المستدعي على نفس المضيف وحيز الشبكة الذي يصل إلى `127.0.0.1` الخاص بالتطبيق (الذي يستمع على loopback فقط).

تنبيه للمبرمج: المجدول الداخلي الحالي لا يستدعي `prepareDue` للنشر؛ توجد العملية يدويًا أو عبر نقطة النهاية الاختيارية. pause gate يغطي الآن كلا المسارين (scheduler/event routing ومسار `/api/automation/*` الخارجي) — راجع `isPaused` في `src/application.js`.

## 10. CRM والمبيعات والمتابعات

يدعم B2C وB2B ومصادر INBOUND وRESEARCH. الهاتف بصيغة دولية، مع normalization ومنع تكرار معرف الاتصال. B2B البحثي يتطلب شركة ومصدرًا ومحفز شراء مؤرخًا وتقييم ملاءمة ودليل فحص. لا يوجد حاليًا crawler يولد شركات حقيقية تلقائيًا من الشبكات.

المراحل: NEW، QUALIFIED، QUOTE_SENT، DEMO، POST_PURCHASE، PARKED، WON، LOST. توجد مدينة واحتياج ورابط منتج وكمية وقيمة تقديرية وميزانية وتوقيت ودرجة اهتمام ومسؤول وموعد مراجعة. `expectedVersion` يحمي من الكتابة فوق تعديل آخر. إعادة فتح صفقة مغلقة مقيدة بالمالك. تجاوز قيمة 100,000 ريال يفعّل humanHold وفق القاعدة الحالية.

المحادثات تُسجل يدويًا، مع eventKey لمنع التكرار. رسالة واردة جديدة توقف المتابعة حتى المراجعة، ثم تصدر CUSTOMER_MESSAGE_RECEIVED لتوجيه وكيل المبيعات. تسجيل رسالة بالواجهة ليس استقبال webhook من واتساب.

موافقة Email منفصلة عن WhatsApp؛ إضافة العميل لا تعني موافقته على التواصل. opt-out يمحو الموافقات ويوقف الرسائل. حالات humanHold/replyHold وتغير مرحلة أو نسخة العميل تمنع إرسال اعتماد قديم. إثبات موافقة جديدة ومعالجة holds يتطلب صلاحيات وقواعد الخدمة، وليس مجرد تعديل شارة UI.

ستة أنواع متابعة: بعد العرض السعري، السلة المتروكة، بعد العرض التوضيحي، ما بعد الشراء، إعادة تفعيل عميل، ودورة الميزانية. كل سلسلة ثلاث رسائل AR/EN. البداية بعد 48 ساعة على الأقل، ثم مواعيد بإزاحات 0/48/120 ساعة من البداية. لا أكثر من سلسلة نشطة للعميل. المحتوى قوالب فعلية محفوظة مع رابط المنتج، والاعتماد بشري على البصمة والسياق.

حالات المتابعة DRAFT/APPROVED/READY_FOR_CHANNEL/HOLD؛ قيمة sent من التجهيز صفر لأن الموصل الخارجي غير موجود. لوحة المبيعات تجمع القمع وKanban والعملاء الساخنين والمتأخرات والمحادثات وB2B والعروض والتوقعات والنشاط. توقع الإيراد نموذج موزون للمراحل، وليس توقع ML أو إيراد محصل. عروض السعر مشتقة من مرحلة الفرصة وبياناتها، ولا توجد فواتير أو quote entity/PDF رسمي مستقل.

## 11. ذاكرة العلامة والكتالوج

13 نوعًا حاليًا: brand_voice، product_fact، price_reference، approved_claim، faq، objection، policy، winning_hook، losing_hook، lost_deal_reason، process_rule، customer_pattern، competitor_insight.

كل سجل له key وversion وsource وchangeReason وهوية اعتماد وتاريخ، وقد يرتبط بمنتج أو تاريخ انتهاء. الأحدث فقط لكل key هو الذي يحدد القيمة الحالية. سحب الأحدث أو انتهاؤه لا يعيد إحياء إصدار أقدم. القيد expectedVersion يمنع حفظ نسخة فوق تحديث لم يقرأه المستخدم.

المالك يحفظ السجل المعتمد مباشرة؛ المشغل يقترح معلومة عبر `/api/memory/propose` لتدخل مركز الموافقات. الاقتراح الآلي عبر `propose_memory_update` مشابه في الغرض. **اعتماد الطلب العام يغير حالة approval فقط؛ لا يكتب الذاكرة تلقائيًا.** الواجهة تتيح «تحويل إلى سجل ذاكرة» لتعبئة نموذج الحفظ، وعلى المبرمج ربط الخطوتين إذا أراد دورة ذرية موحدة.

صحة الذاكرة تشمل مصادر قصيرة، حقائق حساسة للوقت دون expiry، منتهيات، وتعارض أسعار. فحص التعارض حاليًا يقرأ أول رقم داخل النص ويقارنه بسعر المنتج؛ قد يكون الرقم مواصفة وليس سعرًا، لذا هو heuristic يحتاج مراجعة وتطوير. السعر المقارن آخر snapshot مستورد، وليس استعلامًا حيًا.

عرض استخدام المعلومة يُستخرج من نتائج أدوات قراءة الذاكرة المسجلة فعلًا في agent_tool_calls، وليس من تخمين استخدام الوكيل. لا يوجد vector database أو embeddings أو RAG دلالي أو تدريب تلقائي للموديل.

كتالوج سلة يطبع السعر والمخزون والرابط ووقت/مصدر الجلب، ويحافظ على unknown كـnull. الاستيراد الحالي استبدال snapshot للمنتجات بعد نجاح القراءة. لا توجد إدارة مخزون أصلية أو طلبات أو مرتجعات أو تسوية مالية داخل التطبيق.

## 14. التقارير والقياس

الأسبوع الأحد–السبت بتوقيت الرياض. التقرير الحالي يحسب المؤشرات من المحتوى وCRM والجدولة والتشغيلات والتصعيدات، ويقارن بالفترة السابقة ويحفظ لقطة idempotent للأسبوع. الواجهة تدعم العرض والطباعة إلى PDF عبر المتصفح.

مؤشرات المبيعات مبنية على المراحل والقيم المسجلة، وليست تسوية مبيعات متجر. المؤشرات الخارجية غير المتصلة لا ينبغي تفسير الصفر/الشرطة فيها كصفر أعمال مؤكد. عدد run المستخدم في بعض واجهات الوكيل هو آخر 10 فقط، وتجميع التقرير يُمرر له حد آخر 2000 run؛ هذا ليس تاريخًا غير محدود.

ملاحظات Frost في لوحات content/sales/reporting كثير منها حساب قواعد على بيانات موجودة، ولا تستدعي LLM بمجرد فتح الصفحة. يجب التفريق بين هذه summaries وبين run حقيقي في agent_runs، وعدم بيع كل عبارة UI على أنها استنتاج AI جديد.

## 15. الواجهة وما أُعيد بناؤه

إعادة التصميم أضافت طبقات tokens/fonts/base/components/layout/pages، وAppShell موحدًا وSidebar RTL وTopbar وPageHeader، وبحث Ctrl+K وتنبيهات من البيانات وقائمة حساب. توجد أزرار وبطاقات ومقاييس وbadges وحقول وTabs وDataTable وDrawer/Dialog وToast وTooltip وDropdown وSkeleton/EmptyState. اللقطة الحالية تتضمن تطورًا بصريًا أحدث: Sidebar فاتحًا مع شريط أيقونات كحلي منفصل ولمسة بنفسجية، وبطاقة ترحيب ورسوم donut/sparkline/trend وزر Frost عائم. لذلك صور ونظام ألوان التقرير السابق لا يصفان آخر شكل حرفيًا.

الشاشات العشر: overview، crm، planning، reports، content، agents، knowledge، integrations، audit، users. نُقلت النماذج الكبرى إلى drawers، وصار ملف العميل/المحتوى/الوكيل/المعلومة قابلًا للفتح من مساحة العمل. الجدول يدعم search/sort/pagination على النتائج المحملة، ولا يضيف pagination للخادم.

صفحات المحتوى والذاكرة والتكاملات والفريق توسعت بعد مرحلة التصميم الأولى إلى مراكز تشغيل بملفات مستقلة، لذلك أصبح تقرير `docs/ui-redesign-report.md` مرجعًا تاريخيًا لا قائمة نهائية بكل الوظائف الحالية.

التحميل ما زال يجلب عدة صفحات ويعيد رسمها في `render()` عند العديد من العمليات. لا store مركزي منظم أو lazy loading شامل. توجد state module-level وعقد DOM مشتركة، واستيراد متبادل بين بعض وحدات العرض. هذا دين تقني يجب التعامل معه باختبارات وعدم إعادة كتابة عمياء.

## 18. نتيجة الاختبارات وحدود ما ثبت

**التنفيذ الحالي بتاريخ التقرير:** `npm test` نجح: 145 اختبارًا، صفر فشل. تشمل الخدمات الأساسية والمصادقة والامتثال وCRM والتقويم والذاكرة والتوليد والعقود والتقارير والمحرك والأحداث والجدولة ومراكز التشغيل وإدارة الفريق وحماية آخر مالك.

**الاختبار الحالي للواجهة:** `npm run test:ui` توقف في صفحة الذاكرة منتظرًا زر «اعتماد معلومة» بالاسم القديم. التوقف عند selector لا يثبت فشل API أو فشل حفظ الذاكرة، لكنه يعني أن الاختبار غير متزامن مع الواجهة الحالية ولم يُكمل بقية الرحلة.

**الدليل التاريخي:** قبل الإضافات الأحدث، نجحت 40 حالة عرض و12 رحلة وظيفية، مع صفر أخطاء متصفح/axe/overflow في ذلك الوقت. ملف `artifacts/ui/qa-report.json` يخص تلك اللقطة؛ لا تستخدمه منفردًا لقبول النسخة الأحدث.

**فحص التسليم الجديد:** `scripts/handoff-audit.mjs` أنشأ قاعدة مؤقتة بلا مفاتيح وبلا scheduler، وفحص الصفحات العشر على 1440 و1920 و768 و390. النتيجة: 40 حالة عرض مكتملة، صفر أخطاء متصفح، وصفر تجاوز أفقي للصفحة. رصد axe قاعدة color-contrast في 40/40 حالة، بإجمالي 1384 ظهورًا لعناصر عبر الحالات؛ العدد يتضمن تكرار العناصر المشتركة وأحجام الشاشات، وليس 1384 عيبًا مستقلًا. لم يرصد قواعد مخالفة أخرى في نطاق هذا الفحص. يلزم إصلاح الألوان وإعادة القياس قبل ادعاء مطابقة الوصولية.

يحفظ الفحص صورًا ونتائج و23 جدولًا وبصمات 91 ملفًا، مجموعها 7331 سطرًا ضمن src/public/tests/agents/schemas فقط، في `artifacts/handoff/evidence.json`. عدد السطور ليس عدد سطور التنفيذ وحدها ولا مقياس جودة أو اكتمال. وقت الالتقاط المسجل `2026-09-10T01:35:21.683Z`. هذا smoke لحالات فارغة بحساب مالك، وليس بديلًا لتغطية المحتوى الممتلئ والأدوار الثلاثة والعمليات الإدارية الجديدة. سياق فحص axe منفصل ويسمح بحقن أدوات القياس؛ التصفح والصور يستخدمان CSP التطبيق الأصلية.

الاختبارات تستخدم mocks لاستجابات المزود عند فحص AI؛ ليست إثبات نشر حي أو جودة ردود نموذج مدفوعة. لا يوجد في هذا التقرير إثبات تحقق هدف 14 يوم نشر أو 50 محادثة أو الرد خلال خمس دقائق أو جودة العربية في سيناريوهات عملاء حقيقية.

نقاط إضافية للمراجعة: HUMAN_REVIEW يشترط escalation_required في validator، ثم runtime يعطي أولوية ESCALATED قبل WAITING_APPROVAL؛ بعض الحالات المعلنة قد لا تكون قابلة للوصول كما يتوقع UI. وL0 «مسودة فقط» لا يمنع تعديل سجل CRM فعليًا. هذه أمثلة على الحاجة لفصل مستوى الاستقلالية، حالة قرار النموذج، حالة التشغيل، وحالة كيان الأعمال.

## 20. ما لم يُنفذ من المنتج المطلوب أصلًا

لا نشر يومي حقيقي للقنوات الأربع. لا inbound webhook موحد لمحادثات المنصات. لا إرسال أو متابعة خارجية فعلية. لا عروض سعر رسمية أو PDF مستقل أو تحويل دفع/طلب متجر. لا بحث سوق/عملاء آلي موثق متصل بالويب. لا Canva asset فعلي أو مكتبة رفع ملفات/تحقق أبعاد وصيغ. لا GA4/UTM/attribution أو مزامنة نتائج اجتماعية. لا loop تعلم يقيس نتيجة منشور حقيقي ثم يغير استراتيجية مستقبلية تلقائيًا بضوابط.

لا multi-tenancy أو billing أو تطبيق هاتف مستقل أو إدارة مهام مسندة للأفراد أو دعوات فريق بالبريد أو OAuth token rotation أو SSO/MFA. لا CI/CD أو Docker deployment أو OpenAPI أو مراقبة تشغيل مركزية ثبت وجودها في قائمة الملفات المفحوصة. هذه ليست كلها ضرورية للنسخة المحلية، لكنها لا يجوز الادعاء بوجودها.

## 21. خطة استكمال عملية للمبرمج

### الحزمة الأولى: تثبيت النسخة وإزالة الالتباس

احفظ نسخة مصدر موثقة مع lockfile وبصمات ودون أسرار، وحدّث اختبارات UI والوثائق ومصفوفة الصلاحيات. افحص المسارات التي يقرأها reviewer، وإغلاق التصعيد، ومعنى L0، وربط أهلية الترقية. معيار القبول: unit/API/E2E ناجحة للثلاثة أدوار، وعدم الاعتماد على إخفاء زر للحماية.

### الحزمة الثانية: تقوية Runtime والجدولة

وحّد إعداد AI وعقود الأدوات، وأزل تضارب prompt، وأضف قفل tick وbackoff وحدود تكاليف وتعافي التشغيلات. ضع outbox أو queue مناسبة للحجم. معيار القبول: اختبارات انقطاع وإعادة تشغيل وتكرار و429 وtimeout دون كتابة مضاعفة أو إرسال غير معتمد.

### الحزمة الثالثة: اتصال إنتاجي واحد كامل

اختر مع مالك المشروع أولوية واضحة: قناة WhatsApp/البريد للمبيعات أو منصة نشر للمحتوى. نفّذ الحساب والتفويض والموصل وwebhook إن لزم وتخزين external IDs وإعادة المحاولة والموافقة. معيار القبول: حدث حقيقي واحد كامل موثق ثم تجارب failure، دون تعميم نجاح خدمة على الخدمات الأخرى.

### الحزمة الرابعة: المحتوى والتصميم والنشر

اربط الأصل البصري والنسخ والامتثال والجدولة بموصل النشر، وأضف فحص متطلبات media لكل منصة وحالة منشور ورابطه. معيار القبول: نشر محتوى معتمد فقط، وإلغاء اعتماد نسخة معدلة، وتتبع فشل/نجاح فعلي بدل READY_FOR_CONNECTOR.

### الحزمة الخامسة: المبيعات والطلبات والقياس

استقبال رسائل حقيقية، ردود ضمن سياسة الحساب، متابعة بموافقة القناة، quotes وorders، ثم attribution وKPIs. معيار القبول: سيناريو عميل كامل من رسالة إلى قرار/إغلاق، مع opt-out ومنع التكرار وتدخل بشري.

### الحزمة السادسة: الإطلاق والمراقبة

تهيئة الاستضافة/HTTPS والجلسات وbackup/restore والمراقبة والسجلات والمناوبات. نفّذ تجربة فعلية بأهداف النطاق الأصلية ثم قيّم الاستقلالية تدريجيًا. لا يُحدد زمن/سعر كل حزمة دون اختيار القناة وحساباتها وحجم البيانات ومستوى الضمان المطلوب.

## 22. البيانات والقرارات المطلوبة من صاحب المشروع

حسابات المنصات الرسمية وصاحب صلاحية التفويض، وتحديد Instagram الأساسي وFacebook، وبيانات Anthropic وسلة عبر قناة أسرار آمنة. مصادر المنتجات والأسعار والادعاءات والسياسات والضمان والشحن والخصومات المعتمدة. حدود الصفقات والتصعيد وساعات العمل ومسؤول المراجعة. تحديد ما إذا كان فصل المراجع عن المعتمد إلزاميًا، وما إذا كان L0 يسمح بتعديلات CRM محلية. اختيار قناة الإطلاق الأولى وسياسة نشر المحتوى واستضافة النظام ومدة الاحتفاظ بالبيانات.

لا تطلب من المستخدم إرسال المفاتيح داخل هذا المستند أو commit أو دردشة مشتركة مع فريق غير مخول.

## 23. قائمة استلام المبرمج

1. افتح package.json وREADME وهذا التقرير، ثم راجع server.js قبل البدء في تعديل UI.
2. ثبت Node و`npm ci` وشغّل 145 اختبارًا؛ وثق أي فرق في العدد أو النتائج.
3. افحص `artifacts/handoff/evidence.json` وبصمات الملفات لمطابقة لقطة التقرير.
4. شغّل بقاعدة مؤقتة أولًا، ولا تصدر قاعدة العميل أو كلمات مروره إلى بيئة التطوير المشتركة.
5. اقرأ domain/planning لمعنى البصمة والاعتماد قبل تعديل محتوى معتمد.
6. اقرأ crm/permissions/tools معًا؛ لا تخلط دور المستخدم ومستوى الوكيل.
7. راجع GAP-01 إلى GAP-28، وحدد المتطلبات الملزمة ونقطة قبول لكل إصلاح.
8. حدث اختبارات UI بعد تغييرات النصوص والـIDs ولا تترك نجاح unit tests يغطي تعطل الرحلة.
9. لا تعتبر token موجودًا أو badge CONNECTED دليل اتصال؛ اطلب تنفيذًا حيًا موثقًا آمنًا.
10. سلّم changelog واختبارات وbackup/restore وخطة رجوع مع كل إصدار قابل للتشغيل.
