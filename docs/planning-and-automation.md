# التقويم والجدولة وحزمة الموافقات

## التشغيل داخل التطبيق

1. أنشئ تقويمًا من تاريخ تختاره لمدة 30 يومًا. الخانات تمثل خطة محتوى، ولا تحتوي منشورات أو نتائج مولدة وهمية. تكرار الطلب أو تداخل الفترات لا يكرر الخانات ولا يمحو القائم.
2. جهّز مسودة للمنصة والتاريخ. أدخل النص الإنجليزي لـLinkedIn ورابط الأصل البصري لـInstagram. يجب أن يكون الأصل متاحًا عبر HTTPS؛ التطبيق لا يرفع الملفات ولا يفحص أبعادها تلقائيًا.
3. راجع النصوص والرابط والأصل البصري ثم اعتمدها. تُحسب بصمة تشمل النصين والأصل والتاريخ والمنصة. عناصر النسخ الأقدم التي لا تحمل بصمة تحتاج إنشاء نسخة معدلة وإعادة المراجعة.
4. اختر المحتوى المعتمد وحدد الموعد بتوقيت الرياض. تُحجز خانة واحدة لكل منصة ويوم. LinkedIn الأحد والثلاثاء والخميس فقط. رابط الأصل وحده لا يضمن ملاءمته لواجهة نشر المنصة؛ ذلك ضمن مرحلة الموصلات القادمة.
5. «تجهيز المواعيد المستحقة» يعيد فحص الاعتماد وينقل العناصر الصالحة إلى READY_FOR_CONNECTOR. لا توجد استدعاءات نشر، ولا تتحول العناصر إلى PUBLISHED. الأرقام في هذه القائمة ليست منشورات منشورة.
6. يمكنك إلغاء الجدولة. تعديل محتوى معتمد يتاح للمالك ويُنشئ نسخة جديدة DRAFT، ويحتفظ بالنص القديم SUPERSEDED ويلغي مواعيده. الرفض أيضًا يلغي الجدولة؛ لا يُورث اعتماد قديم للنسخة الجديدة.

المراجعة البشرية لكل اللغات والأصل مطلوبة. النص الإنجليزي والمرجع البصري جزء من البصمة، وتغيّرهما يبطل تطابق الاعتماد. الخانات تُربط عند الجدولة، لذلك عبارة «غير مجدول» لا تعني بالضرورة عدم وجود مسودة.

## الحزمة اليومية

الواجهة تعرض معاينة حية لقرارات المراجعة والاعتماد حتى الغد، ومحتوى الغد، والخانات غير المجدولة والمواعيد الموقوفة. حفظ الحزمة ينتج لقطة واحدة لكل يوم بتوقيت الرياض. تكرار الطلب يرجع اللقطة نفسها، والواجهة تعرض آخر 14 حزمة محفوظة. لا تُرسل إلى واتساب أو البريد في هذه المرحلة. تشمل اللقطة النص العربي والإنجليزي والرابط والأصل والبصمة؛ إحصاءات المبيعات والنشر غير المتصلة تبقى null.

هذه الحزمة، والتقرير الأسبوعي، ومسح فجوات المتابعة تُشغَّل تلقائيًا من الجدولة الداخلية (`src/runtime/scheduler.js`) — دورة واحدة داخل عملية Node نفسها، بلا أي منصة أتمتة خارجية ولا Redis ولا Queue منفصل. هذا يعمل بمفرده طالما عملية الخادم تبقى حية.

## نقطتا نهاية اختياريتان للمحفز الخارجي

في بعض بيئات الاستضافة (مثل الاستضافة المشتركة التي تُعيد تشغيل العملية بين الطلبات) لا يمكن ضمان بقاء عملية Node حية باستمرار لتشغيل الجدولة الداخلية بمفردها. لهذه الحالة فقط، توجد نقطتا نهاية HTTP محليتان اختياريتان، تكرران بالضبط ما يفعله الجدولة الداخلية أصلًا (لا منطق أعمال إضافي ولا نشر خارجي):

| المسار | العملية |
|---|---|
| GET `/api/automation/status` | تأكيد الاتصال والنطاق |
| POST `/api/automation/daily-brief` | حفظ حزمة اليوم مرة واحدة (idempotent) |
| POST `/api/automation/prepare-due` | تجهيز المستحق محليًا دون نشر |

### الإعداد

1. أنشئ سرًا عشوائيًا بطول 32 حرفًا أو أكثر وضعه في `AUTOMATION_TOKEN` داخل `.env`، ثم أعد تشغيل الخادم.
2. اجعل أي مشغّل خارجي يستطيعه بيئتك (Cron، Windows Task Scheduler، خدمة جدولة سحابية، أو أي أداة أتمتة عامة تدعم HTTP Request مجدولة) يرسل POST إلى العنوانين أعلاه، مع ترويسة `X-HyperCool-Token: <السر نفسه>`، على نفس المضيف وحيز الشبكة الذي يمكنه الوصول إلى `http://127.0.0.1:3000` (التطبيق يستمع على loopback فقط).
3. اختبر الاستدعاء يدويًا (مثلًا عبر curl) قبل ربطه بأي جدولة متكررة.

لا يوجد أي اعتماد معماري على أداة أتمتة بعينها هنا — هاتان نقطتا نهاية HTTP عاديتان في Backend التطبيق نفسه؛ أي أداة تستطيع إرسال POST مع ترويسة تعمل، والجدولة الداخلية تغطي نفس العمليات تلقائيًا بدونها.

لا يمنح السر صلاحيات المالك أو المراجعة أو تعديل المحتوى أو توليد AI مدفوع. لا يوجد مسار «أعد النشر بعد مهلة»؛ تسوية نتائج النشر غير المحسومة لم تُنفذ لأن موصلات النشر نفسها لم تُربط بعد.

## التحقق والحدود

اختبارات محلية تغطي التقويم وتداخل الفترات، التوقيت، بصمة الاعتماد، اختلاف النسخة، إلغاء المواعيد، حدود الصلاحيات، حزم اليوم، وحدود رمز المحفز الخارجي (`AUTOMATION_TOKEN`).

استراتيجية AI الكاملة والتصميم الآلي ووكيل الامتثال الآلي ما زالت مراحل لاحقة. هذه المرحلة تضيف خطة قواعد ثابتة ومراجعة بشرية وتجهيزًا محليًا للجدولة، ولا تدعي اكتمال Content Pod في الإنتاج.
